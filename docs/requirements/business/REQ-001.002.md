# REQ-001.002 Read and Edit Project Configuration

## User Story

As a project maintainer, I want to inspect and change configuration values so that Papyrus uses settings appropriate to my project.

## Group

REQ-001 Project Setup and CLI Access

## Criticality

Must have

## Description

The user can list effective configuration keys and defaults, get one effective value, persist a value, and unset a key to fall back to its default. Keys support dotted notation. A document-type entry is addressed beneath `document_types.<slug>`; its `group` and `member` blocks are nested mappings, and its `fields` (or `group.fields` and `member.fields`) is a YAML sequence of field mappings (REQ-007.002).

**Selector paths.** A configuration leaf is addressed by the selector path `document_types.<slug>.<path>`. A field sequence element is addressed by key, as in `document_types.req.member.fields[story].heading`, or by zero-based index, as in `document_types.req.group.fields[0].required`; both forms resolve to the same element. `config get` and `config set` accept one selector, `config list` prints the full effective configuration with seed-filled values, and each leaf in that listing is addressed by its selector path, with field properties using the key selector. A selector that does not resolve to a leaf — an unknown key, a keyed selector that matches no unique field, or an out-of-range index — is rejected with a validation outcome.

**Set, unset, and materialization.** `config set document_types.<slug>.<path> <value>` materializes only the target entry when the file does not declare it, applies the single change, validates the resulting configuration, and writes it; it never materializes the whole seed set. For a nested leaf it creates only the path it needs. `config unset` of a scalar removes the override so the seed value applies again; `config unset` of a flat collection (`statuses`, `api_aliases`, or `slots`) resets it to the seed collection for the slug. A field sequence is not a flat collection: adding, removing, reordering, or unsetting a field is a configuration file edit (REQ-007.002).

Values supplied to `set` follow the key's shape. A scalar key keeps the current behavior: the supplied value is parsed as a YAML scalar. A list-valued key — the task status list `statuses`, each document type's `statuses`, and the flat `api_aliases` and `slots` collections (REQ-007.002) — accepts a comma-separated list, for example `papyrus config set document_types.req.statuses active,archived`, and writes it as a YAML flow sequence. In this form a comma is always a separator and cannot be escaped, so a value that must contain a comma can only be set by editing `papyrus.config.yml` directly. An empty value for a list-valued key is rejected as invalid rather than written as an empty list. `fields` and the role field sequences are not list-valued keys: they are sequences of mappings and are never written from a comma-separated value.

`papyrus init` writes each document type as a minimal entry: only `prefix` and `directory`, plus `enabled` when the interactive walkthrough disables that artifact (REQ-001.006); every other value comes from the seed. The configuration that would result from a `set` or `unset` is validated before it is persisted; an invalid result is refused and nothing is written (fail-closed).

When an artifact's folder is changed with `papyrus config set` — a document type's `directory`, or `backlog_directory`, `decision_directory`, or `doc_directory` — the entire content of the original folder is moved to the new folder. The move covers every file and subfolder, not only Papyrus-managed records. It happens during the `set` command (not later, not lazily), it is a move rather than a copy, and it is atomic: if any entry cannot be moved, for example because an entry with the same relative path already exists at the destination, nothing is moved, both folders are left as they were, the configuration value is not persisted, and the command reports a conflict (REQ-001.004). After a successful move the original folder no longer holds the moved content.

The effective configuration is validated at load (REQ-007.002), including each document type's `statuses` and `default_status`. While the effective configuration is invalid, every command fails closed with a validation outcome (REQ-001.004) except the repair surfaces: `papyrus config get|set|unset|list` load the configuration tolerantly, validate the configuration that would result from the requested change, and refuse a write that would still be invalid; `papyrus init --force` replaces the file with the generated default configuration; `papyrus check` loads the configuration tolerantly, reports the configuration findings, and runs the checks that do not depend on the effective `document_types` set (REQ-001.008). A broken configuration is therefore always repairable through Papyrus.

## Acceptance Criteria

- `papyrus config list` prints effective keys including defaults.
- `papyrus config list` prints the full effective configuration, seed-filled values included, and addresses each leaf by its selector path, with field properties using the key selector.
- `papyrus config get <key>` prints that key's effective value.
- `papyrus config get` and `papyrus config set` accept one selector.
- A nested document-type key is addressed with dotted notation, such as `document_types.req.enabled`.
- The `group` and `member` blocks and the `fields` sequence are nested configuration data addressed by selector paths, not by dotted scalar keys.
- A field sequence element is addressable by key, as in `document_types.req.member.fields[story].heading`, and by zero-based index, as in `document_types.req.group.fields[0].required`, and both forms resolve to the same element.
- A selector that does not resolve to a configuration leaf — an unknown key, a keyed selector that matches no unique field, or an out-of-range index — is rejected with a validation outcome.
- `papyrus config set document_types.<slug>.<path> <value>` materializes only the target entry, applies one change, validates the result, and never materializes the whole seed set.
- `papyrus config unset <key>` removes the configured key and uses its default.
- `config unset` of a scalar removes the override so the seed value applies again; `config unset` of a flat collection (`statuses`, `api_aliases`, or `slots`) resets it to the seed collection.
- `papyrus config set <key> <value>` persists a scalar key's value as a YAML scalar, unchanged from the current behavior.
- A comma inside a scalar value is part of that scalar and is not treated as a list separator.
- For a list-valued key (`statuses`, `document_types.<slug>.statuses`, `api_aliases`, and `slots`), `papyrus config set <key> <value>` accepts a comma-separated value such as `active,custom-status,archived` and writes it as a YAML flow sequence.
- A list value written with `config set` is read back by `config get` and `config list` as the same values in the same order.
- Commas in a list value are separators and have no escape form: `active\,archived` is not read as an escaped comma, and the resulting value is rejected as invalid because a comma is not a permitted status character (REQ-007.002).
- An empty value for a list-valued key is rejected with a validation outcome (REQ-001.004); neither an empty list nor any other value is written.
- `fields` and the role field sequences are never written from a comma-separated value; adding, removing, reordering, or changing a field is a configuration file edit.
- `papyrus init` writes each document type as a minimal entry with `prefix` and `directory`, plus `enabled` when the interactive walkthrough disables that artifact.
- A list value is validated as the configuration that would result before it is persisted: a value that violates the `statuses` rules of REQ-007.002, for example one that omits `active`, is refused with a validation outcome and nothing is written.
- Adding a `document_types.<slug>` entry creates a new document type whose slug becomes its CLI command name (REQ-007.002).
- A configuration with an invalid document slug or a slug that collides with a built-in command name is rejected with a validation outcome (REQ-001.004, REQ-007.002).
- `document_types.<slug>.statuses` and `document_types.<slug>.default_status` are ordinary configuration keys: they are read by `config get` and written by `config set`, and their values are validated at load as described in REQ-007.002.
- While the effective configuration is invalid, every command fails closed with a validation outcome (REQ-001.004) except `config get`, `config set`, `config unset`, `config list`, `init --force`, and `check`.
- `config get|set|unset|list` load an otherwise invalid configuration, validate the configuration that would result from the requested change, and refuse to write a configuration that is still invalid.
- `init --force` can replace an invalid configuration file with the generated default configuration.
- `papyrus check` loads an invalid configuration tolerantly, reports the configuration findings, runs the checks that do not depend on the effective `document_types` set, and exits with a validation outcome when findings exist (REQ-001.008).
- When an artifact's folder is changed via `papyrus config set`, every file and subfolder of the original folder is moved to the new folder.
- The move is performed as part of the `set` command, not lazily; afterwards the original folder no longer holds the moved content and is removed once empty.
- If the move cannot complete (destination entry conflict or write failure), the command reports a conflict, persists no configuration change, and leaves both folders unchanged.
- The configured task statuses must be unique, and the configured default task status must be one of them.
- With default settings, new tasks start at `ToDo` and the ordered statuses are `ToDo`, `Initiated`, `Refined`, `Implemented`, `Validated`, and `Done`.

## Description

Feature milestone for the 2026-11-15 requirement set: **REQ-01.008** (`papyrus check`), **REQ-06.015** (content width and collapsible navigation), **REQ-06.016** (uniform list layout), **REQ-06.017** (offline math and Mermaid diagrams), plus the 2026-11-15 edits to REQ-01.002, REQ-01.004, REQ-02.003, REQ-05.007, REQ-06.013, REQ-06.014, and REQ-07.002.

**Authority.** ADR-0025 (KaTeX), ADR-0027 (vendored assets), ADR-0028 (browser shell, list, width, nav), and ADR-0029 (`check`) are Accepted. ADR-0026 (Mermaid) is **Proposed**: TASK-146, TASK-148, and TASK-150 carry a `blocked` label and no diagram code, asset, notice, or CSP relaxation lands before formal acceptance. PlantUML is out of scope.

**Scope.** Four dependency-ordered tracks that share one milestone because they touch the same binary, the same browser shell, and the same package verification:
1. `check` — read-only scanners over registry descriptors, tolerant self-load, `CommandOutput.exit_code`, exit 4, `--json`, then `--fix` duplicate-ID repair, then the reserved slug and documented command surface.
2. Browser shell — one shell module, a server-side `PageWidth` contract, one shared list layout with per-family characterization tests, collapsible navigation persisted in `localStorage`, and the width classes for the uncapped board and full-width diagram regions.
3. Vendored assets and rendering — the static asset table, SHA-256 manifest, `.deb` notices, and the 12 MiB budget, then KaTeX math and gated Mermaid diagrams.
4. Specification revision and verification — packaging/browser specifications follow the landed contract, then packaged-asset and end-to-end verification.

**Sequencing.** TASK-137, TASK-141, TASK-143, and TASK-147 have no dependency and start in parallel. `check --fix` follows the scanners; the family migration follows the shell foundation; math follows the asset table; diagrams follow math and the ADR-0026 gate. Verification is last.

**UI gates.** TASK-142, TASK-144, and TASK-147 change a browser view: when refinement produces a UI mockup, implementation does not merge until the mockup is approved through `ui-designer`; a recorded no-mockup waiver is the alternative.

**Boundaries.** No release milestone and no release ticket are created; the release vehicle for m-17 to m-21 remains an owner decision. No mockup preview route, no PlantUML, no new Rust crate, no build-toolchain step, and no CLI change beyond `check` are in scope. Nothing is marked Done by planning.

# REQ-007.001 Organize Artifacts into Three Categories

## User Story

As a project contributor, I want every artifact to belong to a known category so that I know which lifecycle applies and what configuration can change.

## Group

REQ-007 Artifact Categories and Config-Defined Document Types

## Criticality

Must have

## Description

Papyrus manages exactly three artifact categories:

- **backlog** — tasks, milestones, and releases.
- **decision** — decision records.
- **document** — every document type declared in the project configuration.

Each record type belongs to exactly one category, and the category owns the lifecycle of its records. A document type's document model and field sequences describe record content and storage only: they add, remove, rename, and reshape no status and introduce no per-type lifecycle (REQ-007.004).

**Category lifecycles.** Task statuses are configurable through `statuses` and `default_status` (REQ-001.002). Within the backlog category the other lifecycles are fixed: a milestone is `open`, then `closed`, then `archived`, and a release is `planned`, then `released`, then `archived` (REQ-002). Decision records use the fixed statuses `proposed`, `accepted`, `rejected`, `deprecated`, `superseded`, and `archived` (REQ-004). Document types use a storage state plus optional workflow statuses, described below.

**Document storage state.** A document record is either archived or not archived. The state is decided by location and mirrored in the status value: archived means `status: archived` and a file in the type folder's `archived/` subfolder; not archived means a file in the type folder and a status of `active` or a declared custom workflow status. The `archive` command is the only writer of `archived`, for every document model (REQ-005.007).

**Custom workflow statuses.** A document type may declare custom statuses in its `statuses` list. They are front-matter values only: they cause no file move, define no folder per status, introduce no lifecycle, and change nothing about listing, archiving, or deleting. A record carrying a custom status is a non-archived record in the type folder and remains archivable. A new record starts at its type's `default_status` when one is configured, otherwise `active`.

**Status list invariants.** `active` is always available and describes any non-archived state; it is not a declared status. `archived` is reserved for the storage state. A declared `statuses` list therefore contains neither value, and listing either is a configuration error (REQ-007.002). A status list may be empty, which leaves `active` as the only workflow status. Custom statuses are available only for front-matter-backed document types. A `SingleHtmlMockup` type keeps its state in its HTML metadata with the fixed states `pending`, `approved`, and `archived`, declares no custom status, and has no `status` verb (REQ-005.008).

**The status verb.** `papyrus <document-slug> status <ID> <VALUE>` sets a record's front-matter status to `active` or to a declared custom status, changes nothing else, and refreshes `updated_date`. It never archives: the value `archived` is rejected with a validation outcome (REQ-001.004) that names the `archive` command as the only way to archive, and no file moves. An archived record is likewise rejected with a validation outcome that names it as archived; the command changes nothing and never restores it. No create, edit, or field option sets a status (REQ-005.011).

**Fixed configuration boundary.** Configuration cannot add, remove, or rename a category, cannot change a fixed lifecycle, and cannot change the document storage state or the meaning of `active`. Declaring custom statuses is configuration of front-matter values only. A decision's `archived` is a status value that moves no file, while a document's `archived` is a storage state; a document is never `deprecated`.

## Acceptance Criteria

- Papyrus manages exactly three artifact categories: backlog, decision, and document.
- Tasks, milestones, and releases belong to the backlog category, decision records to the decision category, and every document type declared in the configuration to the document category.
- Each record type belongs to exactly one category, and the category owns its lifecycle.
- A document type's document model and field sequences add, remove, rename, and reshape no status and introduce no per-type lifecycle.
- Task statuses come from `statuses` and `default_status`; the milestone lifecycle is `open -> closed -> archived` and the release lifecycle is `planned -> released -> archived`, both fixed.
- Decision records use only `proposed`, `accepted`, `rejected`, `deprecated`, `superseded`, and `archived`.
- A document record is archived exactly when it carries `status: archived` and lives in its type's `archived/` subfolder; otherwise it is not archived and lives in the type folder.
- A document type may declare custom workflow statuses; a custom status is a front-matter value that moves no file, creates no per-status folder, and changes no lifecycle.
- A record carrying a custom status remains a non-archived record in the type folder, remains listed, and remains archivable and deletable.
- `active` is always available and is not a declared status; `archived` is reserved for the storage state.
- A declared `statuses` list contains neither `active` nor `archived`, and listing either is a configuration error.
- A declared `statuses` list may be empty, leaving `active` as the only workflow status.
- A new document record starts at its type's `default_status` when one is configured, otherwise `active`.
- The `archive` command is the only writer of `archived`, and no file moves for any other status value.
- `status <ID> <VALUE>` sets `active` or a declared custom status, changes only the status, and refreshes `updated_date`.
- `status <ID> archived` is rejected with a validation outcome that names the `archive` command as the only way to archive, and no file moves.
- `status <ID> <VALUE>` on an archived record is rejected with a validation outcome that names the record as archived; nothing changes and nothing is restored.
- Configuration cannot add, remove, or rename a category, change a fixed lifecycle, or change the document storage state.
- A decision's `archived` is a status value that moves no file, and a document is never described as `deprecated`.

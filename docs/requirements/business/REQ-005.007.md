# REQ-005.007 Archive and Delete Document Records

## User Story

As a project maintainer, I want to archive or delete a document record so that inactive documentation leaves the working set while its identity survives until I deliberately delete it.

## Group

REQ-005 Project Documentation Management

## Criticality

Must have

## Description

**Storage state and status.** A document record is either *archived* or *not archived*. The state is decided by file location: a record is archived exactly when its file lives in the `archive/` subfolder of its type's folder. The stored `status` value is independent of the storage state: `archive` moves the file and changes no status, and it never defines the state; a record outside `archive/` is not archived, whatever its status value. A record that is not archived lives in the type's folder and carries `active`, which means no finer state, or one of the custom workflow statuses its type declares (REQ-007.001). A workflow status is front-matter data only: it never moves a file and never changes the storage state.

**Starting state.** A new record starts at its type's `default_status` when one is configured, otherwise `active`, and the value is written into the front matter. `active` is always available and is never declared in the type's status list; `archived` is not a status value and is never declared either (REQ-007.002).

**The archive command.** `papyrus <slug> archive <ID>` moves the record's file into the `archive/` subfolder of the type's configured directory. Two things must not be confused: the command is `archive`, and the destination is `archive/`. The file move is the state change; archiving changes no status. Archiving preserves the record identifier (REQ-001.005). Archived records are hidden from lists, search, and the browser — unless a search explicitly includes archived records (REQ-009.001) — and the browser shows the shared not-found page for them (REQ-005.017). For a `formatted-record` record the file moves the same way (REQ-005.008).

**No restore.** No command returns an archived record to a non-archived state. This is a product decision, not a missing capability. Only the `archive/` subfolder is recognised as archive storage: a `deprecated/` subfolder is not read as archived, is not migrated, and is not inventoried by any command, including `papyrus check`.

**Delete.** `papyrus <slug> delete <ID>` permanently removes a record. A record that is not archived is archived first and then removed. Deletion asks for confirmation, and `--force` skips the prompt. A deleted record leaves no file, and its identifier is not reused: allocation is the highest observed number plus one across the type's folder and its `archive/` subfolder, with no high-water mark, so deleted numbers generally remain gaps and deleting the highest record makes its number available again.

**grouped-record.** Archive and delete apply per record. Archiving or deleting a group record changes none of its members, and each member keeps its file, status, and identifier (REQ-005.001).

The rules of this requirement are identical for all three document models and do not depend on a type's field sequence or role field sets.

## Acceptance Criteria

- A record is archived exactly when its file lives in the `archive/` subfolder of its type's folder.
- A record outside `archive/` is not archived, whatever its `status` value.
- A record that is not archived lives in the type's folder and carries `active` or a declared custom workflow status.
- An archived record keeps the status it had before archiving.
- A new record starts at its type's `default_status` when one is configured, otherwise `active`, and the value is written into the front matter.
- A custom workflow status causes no file move and creates no per-status folder.
- The `archive` command moves the file into the type's `archive/` subfolder`.
- Archiving preserves the record identifier.
- Archived records are hidden from lists, search, and the browser, unless a search explicitly includes archived records (REQ-009.001); the browser shows the shared not-found page for them.
- A `formatted-record` record's file moves in the same way, and archiving changes no metadata status.
- No command returns an archived record to a non-archived state; no restore command exists.
- Only the `archive/` subfolder is recognised as archive storage; a `deprecated/` subfolder is not read, migrated, or inventoried by any command, including `papyrus check`.
- `delete <ID>` permanently removes the record, archiving it first when it is not archived.
- Deletion requires confirmation, and `--force` skips the prompt.
- A deleted identifier is reused only when it was the highest observed number: allocation is the highest observed number plus one across the type's folder and its `archive/` subfolder, with no high-water mark, and lower deleted numbers remain gaps.
- Archiving or deleting a group record of a `grouped-record` type leaves every member's file, status, and identifier unchanged.
- The rules apply to every configured document type and do not depend on a type's document model, field sequence, or role field sets.

# REQ-005.008 Manage SingleHtmlMockup Records

## User Story

As a project contributor, I want to maintain mockup records with an HTML body so that design artifacts can be found, reviewed, approved, updated, and retired.

## Group

REQ-005 Project Documentation Management

## Criticality

Must have

## Description

Every document type declared in the project configuration whose document model is `SingleHtmlMockup` is managed by this requirement. Such a type has one record per plain identifier, its body is HTML, it declares no field sequence, and it carries no YAML front matter: its metadata lives in an HTML metadata comment instead (REQ-005.010).

**Command family.** The verbs are `create`, `list`, `view`, `edit`, `archive`, `delete`, and `supersede`, derived from the document model (REQ-007.003). There is no `status` verb, and a `statuses` or `default_status` declaration on such a type is rejected (REQ-007.002). The `approved` state is reached through the `edit` option `--status approved`.

**Fixed metadata.** The metadata block carries exactly the keys `status`, `task`, `specs`, `refs`, `references`, and `superseded_by`. They are engine-owned record data read from and written to the HTML metadata comment; no key is a field, a CLI field option, or a configuration key. `task` records the associated task identifier, `specs` the UI specification identifiers the mockup realises, `refs` the references to other records, `references` the record's references shown read-only, and `superseded_by` the back-reference to the superseding mockup.

**States.** The states are exactly `pending`, `approved`, and `archived`, in that linear order. Configuration cannot add, remove, or rename them. A new record starts `pending`. A transition that goes backwards or skips a state is rejected, and no transition is possible once a record has been superseded. `edit --status approved` performs the `pending` to `approved` transition, and `--status` accepts no other value. `archive` remains the only path to `archived`: `--status archived` is rejected and writes nothing.

**Create and edit.** `papyrus <slug> create <TITLE> --task <TASK> --spec <SPEC-ID>` creates a record: the title, the associated task, and at least one UI specification are required, `--spec` and `--ref` are repeatable, and the title follows the contract of REQ-005.015 applied to the HTML metadata. `edit` offers the title, the two list-valued metadata controls `specs` and `refs`, and the `--status` option, which accepts only `approved` and only from `pending`; `task`, `references`, and `superseded_by` are read-only, and the browser form offers no status control.

**Supersession.** `papyrus <slug> supersede <old> <new>` records supersession: the superseded record becomes `archived` and stores the superseding identifier in `superseded_by`, and the superseding record is unchanged. Supersession is performed by command only and is never a form control or a field.

**Archive and delete.** Archiving sets the metadata state to `archived`, moves the file into the `archived/` subfolder of the type's directory, hides the record from lists, search, and the browser, and preserves its identifier (REQ-005.007). Deletion permanently removes the record, archiving it first when it is not archived, with confirmation and `--force`. There is no restore command.

**Versioning.** Papyrus does not version a record; version control is provided by the project's version-control system.

## Acceptance Criteria

- The requirement applies to every configured document type whose document model is `SingleHtmlMockup`, and to no other type.
- A record has one plain identifier, an HTML body, no field sequence, and no YAML front matter.
- The command family is `create`, `list`, `view`, `edit`, `archive`, `delete`, and `supersede`; no `status` verb exists for such a type.
- A `statuses` or `default_status` declaration on such a type is rejected.
- The metadata keys are exactly `status`, `task`, `specs`, `refs`, `references`, and `superseded_by`, all read from the HTML metadata comment.
- The states are exactly `pending`, `approved`, and `archived`, and configuration cannot add, remove, or rename a state.
- A new record starts `pending`; a transition to `approved` and then to `archived` is accepted, while a transition that goes backwards or skips a state is rejected with no write.
- `edit --status approved` moves a `pending` record to `approved`.
- `--status` accepts no value other than `approved`, and `--status archived` is rejected with no write.
- The browser edit form offers no status control.
- `archive` is the only path to `archived`, and no transition is possible for a superseded record.
- The title follows the title contract of REQ-005.015 and is held in the HTML metadata.
- `create <TITLE> --task <TASK> --spec <SPEC-ID>` is rejected with one validation outcome and writes no file when the title, the task, or every specification reference is missing.
- `--spec` and `--ref` are repeatable.
- `edit` offers the title, the `specs` and `refs` controls, and the `--status` option, which accepts only `approved` from `pending`; `task`, `references`, and `superseded_by` are read-only.
- `supersede <old> <new>` sets the superseded record to `archived` and records the superseding identifier in `superseded_by`, leaving the superseding record unchanged.
- Supersession has no form control and no field.
- Archiving hides the record from lists, search, and the browser, moves it to the `archived/` subfolder, and preserves its identifier.
- Deletion permanently removes the record, archiving it first when it is not archived, with confirmation and `--force`.
- No restore command exists, and Papyrus does not version a record.

## Open Questions

- Whether the `approved` transition is offered as a command option or only through the metadata block. The linear order and `archive` as the only path to `archived` are fixed; the trigger for `approved` is not.
- Whether any additional document type may declare this model, now that the model is configuration data (REQ-007.004).

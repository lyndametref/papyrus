# UI-002 Papyrus Local Browser (Backlog Records)


## View
backlog-records

## Description
Revised under TASK-206 (MS-030): ordering, markers, and cleanup controls; see sections 4, 4b, 8, 9, 10.
## 1. Purpose and scope

Layout, states, elements, and interactions for extending the local browser to active task, milestone, and release records, reusing the approved MOCK-0001 shell, revised per user feedback: a single combined backlog view, kanban layout, framed tags, bullet-list acceptance criteria, tag-based dependency editing, and a searchable milestone dropdown.

## 2. Shared shell

Header (product name, project name, static offline/bind note), persistent left sidebar `nav` "Document types" with entries (Business requirements, Non-functional requirements, Backlog), `main`, footer, one `h1` per page. Selected entry bold + underline + `aria-current="page"`. The header navigation toggle collapses and expands the sidebar on every page; the default is expanded and the choice persists in `papyrus.nav`, with the navigation expanded and usable without JavaScript.

## 4. Backlog view

- Single view named "Backlog" combining tasks, milestones, and releases.
- Milestones are expandable and collapsible sections (existing behavior, retained); by default only the first milestone that has a non-archived task is expanded.
- Expanding a milestone renders that milestone's tasks as a kanban board: one column per configured task status (REQ-001.002), laid out horizontally within the milestone, in configured status order, with empty-status columns still visible.
- The board is nested inside the milestone section; milestones remain the grouping unit of the view.
- Milestones assigned to a release appear under that release; milestones assigned to no release are grouped together before the first release. Each release boundary is a bold separator that names the release and does not rely on colour alone. Milestone and release ordering follow REQ-006.020: within a release, milestones are ordered by the lowest ordinal among their non-archived tasks, ascending; a milestone with no non-archived task is ordered after every milestone that has one, by milestone ID ascending; milestones with equal lowest ordinals are ordered by milestone ID ascending. Milestones in the no-release group follow the same rule. Releases are ordered by the lowest ordinal among the non-archived tasks in their milestones, ascending; a release with no such task is ordered after every release that has one, by release ID ascending; releases with equal lowest ordinals are ordered by release ID ascending. The no-release group precedes all releases. The order is recomputed from current record data on each render.
- Lifecycle markers (REQ-006.021): the marker 🔘 or ✅ is placed immediately before the title text in the milestone summary and in the release heading, in addition to the record ID and title. 🔘 marks an open milestone or a planned release; ✅ marks a closed milestone or a released release. Archived milestones are not shown and carry no marker. The marker reflects stored lifecycle state.
- Tasks that belong to no milestone appear in their own expandable section, placed after all milestone sections (including all release groups); cards in the section are ordered by ascending task ID and each shows the task ID and title and links to the task record view.
- Cards are ordered by ascending task ID within a column and show at least the task ID and title, linking to the task record view (`/doc/{id}`). Resolved presentation details (TASK-102): cards also show assignee and labels (as framed tags) beneath the ID+title link; columns are equal-width thirds (one per configured status) within a milestone; the release separator is bold with a 2 px bottom border and names the release; the non-drag status control is a compact select dropdown on the card listing all configured statuses with the current status selected; by default only the first milestone that has a non-archived task is expanded (others collapsed); empty columns show the placeholder text "No tasks in this status."
- **Refined under TASK-103.** The status select is paired with a visible `Change status` submit button and sits inside a plain `POST /doc/{id}` form, so the control works with JavaScript disabled and from the keyboard. The script does not auto-submit on select change: a status change is submitted by the button or by dropping the card. Drag-and-drop is script-only enhancement; without the script the card and its form remain fully usable. The board renders an alert with `role="alert"` above the groups when a status change cannot be persisted, and the card stays in its stored column. A task whose stored status is not configured appears in a trailing `Unconfigured status` column. Tasks whose milestone is absent or unresolved appear in an expandable `Tasks without a milestone` section after all milestone sections. After a successful change the board returns with the card's milestone expanded.
- A task's status is changed by dragging its card into another status column, or with an equivalent status control on the card that does not require dragging. Either action persists the status immediately to the task record through the existing browser write contract (ADR-0006 version token, ADR-0013 single write path); the board is not a staging area with a separate save step. The change alters only the status value and preserves every other field of the task. A change that cannot be persisted leaves the card in its original column and reports the failure to the user; after a successful change the value is still shown after the view is reloaded.
- Archived tasks and archived milestones are not shown on the board.
- Empty states and long-title wrapping as in MOCK-0001.
- Presentation details resolved by the MOCK-0002 revision (TASK-102) and recorded above: card contents beyond the task ID and title (assignee + labels); column widths (equal thirds); separator styling (bold, 2 px bottom border, names the release); non-drag status control shape (compact select dropdown); default expansion state (first milestone with tasks expanded, others collapsed); empty-column placeholder text ("No tasks in this status.").

### 4a. Per-milestone `Clean up all` action (TASK-147, MOCK-0017)

- **Placement.** The action is a link labelled `Clean up all`, drawn inside the header of the final configured task status column (the last configured status, `Done` by default), directly beneath that column's status heading and above its first card. Its accessible name names the status and the milestone, for example `Clean up all Done tasks in MS-001`. It appears only in the header of that column of a milestone board: no other column, no `Unconfigured status` column, and no `Tasks without a milestone` section carries it.
- **Visibility.** The action is drawn from configuration only, never from data: it is present whenever the final configured status differs from `active`, including when the column is empty and for a collapsed or closed milestone board. When the final configured status is `active`, no milestone board draws the action.
- **Confirmation warning region.** Activating the action opens a server-rendered region below the milestone heading and above the milestone's columns; it is not a dialog, overlay, or script-driven prompt. While the region is open, the column header no longer shows the `Clean up all` link. Reading order inside the region: a heading that starts with `Warning` and names the milestone and the status; a sentence naming the milestone, stating the count and that archiving removes those tasks from this board and touches no other milestone; a sentence introducing the ID list; the affected task IDs in ascending order, one per bullet, as `<strong>ID</strong> — title`; then the controls.
- **Controls.** One confirm control named `Archive {count} tasks` (submit) and one `Cancel` link. `Cancel` is a plain link back to the board with that milestone expanded; it resolves nothing and archives nothing. The region carries no other control and no close icon.
- **Empty column.** When the column holds no task for the milestone, the action is still offered in the column header before activation. After activation the region keeps the heading and names the milestone and status, then states that the column is empty and that no task will be archived; it contains no confirm control, no form, and only the `Cancel` link.
- **Failure report.** When some archives fail, the board re-renders with an alert region above the release groups. The alert keeps `role="alert"`, a heading (`Clean up all finished with failures`), the page subtitle `Some tasks could not be archived.`, a sentence stating how many tasks were archived out of the total and naming the milestone, and a list of each failed task ID with its message. Successfully archived tasks are absent from the re-read board; failed tasks stay in their column with their status unchanged, and the action is offered again.
- **Meaning is never colour-only.** The action is a text link, the region is introduced by the word `Warning`, the alert is introduced by its heading and counts, and every failed task is named in text.
- **320 CSS px.** Columns stack in configured status order and the warning region keeps its reading order: heading, milestone and count sentence, ID list, controls. The confirm control spans the available width and the `Cancel` link sits below it. In the action state the link sits under the status heading and wraps inside the column; the page gains no horizontal scrollbar.

### 4b. Milestone and release cleanup controls (TASK-206, REQ-006.022)

- **Milestone cleanup.** Each displayed closed milestone shows a cleanup control immediately after its title. Activating it shows a confirmation listing the milestone ID that will be archived; confirming archives that milestone (REQ-003.001) and removes it from the view; cancelling archives nothing.
- **Release cleanup.** Each displayed released release that contains at least one closed milestone shows a cleanup control immediately after its title. Activating it shows a confirmation listing the IDs of the closed milestones in that release that will be archived; confirming archives each listed milestone, one by one; the release itself remains visible and released and is never archived. A released release with no closed milestone shows no cleanup control.
- **Failure handling.** If archiving one milestone fails, the failure is reported for that milestone, the remaining milestones are still archived, and the failed milestone stays visible.
- **Browser-only.** The controls are browser actions only; they add no CLI command and no new write path (ADR-0013). They are distinct from the per-milestone task `Clean up all` action of 4a.
- **Meaning is never colour-only.** The cleanup control is a text link; the confirmation lists affected IDs in text.

## 5. Record views

- Task: metadata block (ID, form, category, status, milestone link-or-text, assignee, labels as framed tags, dependencies links both directions (depends on / depended on by), acceptance criteria as bullet list, comments), description, breadcrumb `Backlog › ID`, single Edit.
- Milestone: metadata (ID, form, category, release), description, breadcrumb.
- Release: metadata, description, breadcrumb.

## 6. Edit forms

- Task: title, description, status, milestone (searchable dropdown), assignee, labels (add/remove tag workflow with search box, same as dependencies), dependencies (tag-adding workflow with search), acceptance criteria (add/remove lines); milestone/release fields as applicable.
- Hidden `version` input plus dashed annotation "Hidden field: version (optimistic-concurrency token)".
- Data-entry fields use the full width of the middle part.
- Pristine, dirty, validation-error (422), conflict (409), and 320 px states.

## 7. Error pages and responsive/a11y

Reused from MOCK-0001: 404 unknown/archived, 400, 403, 405, 415, 500. 320 px list and edit form with sidebar toggle and annotation legend.

## 8. Active elements

List: sidebar links, task card links, milestone expand/collapse, drag handle for status change, per-card status select (non-drag). View: breadcrumb links, Edit, milestone/dependency links. Edit: inputs, textareas, select, search boxes, tag remove/add buttons, Save, Cancel, hidden version. Error: recovery link.

Board, `Clean up all` action (TASK-147): one `Clean up all` link per milestone board, in the final configured status column header; the confirmation warning region's `Archive {count} tasks` submit control and `Cancel` link; no confirm control in the empty-column warning. The failure alert carries no control.

Board, milestone and release cleanup (TASK-206, REQ-006.022): one cleanup control per closed milestone, immediately after its title; one cleanup control per released release that contains at least one closed milestone, immediately after its title; the confirmation region's confirm control (`Archive {n} ...`/`Archive {count} tasks`) and `Cancel` link; no control on a released release with no closed milestone.

# REQ-007.001 Organize Artifacts into Three Categories

## User Story

As a project contributor, I want every artifact to belong to a known category so that I know which lifecycle applies and what configuration can change.

## Group

REQ-007 Artifact Categories and Config-Defined Document Types

## Criticality

Must have

## Description

Papyrus manages exactly three artifact categories:

- **backlog** — tasks, milestones, and releases.
- **decision** — decision records.
- **document** — every document type declared in the project configuration.

Each record type belongs to exactly one category, and the category owns the lifecycle of its records. A document type's document model and field sequences describe record content and storage only: they add, remove, rename, and reshape no status and introduce no per-type lifecycle (REQ-007.004).

**Category lifecycles.** Task statuses are configurable through `statuses` and `default_status` (REQ-001.002). Within the backlog category the other lifecycles are fixed: a milestone is `open`, then `closed`, then `archived`, and a release is `planned`, then `released`, then `archived` (REQ-002). Decision records use the fixed statuses `proposed`, `accepted`, `rejected`, `deprecated`, `superseded`, and `archived` (REQ-004). Document types use a main status plus optional custom statuses, described below.

**Document main status.** Every document type has the main status `active` or `archived`, and these two values are the only ones that affect storage location: an active record is stored in the type's configured folder, and an archived record is stored in that folder's `archived/` subfolder (REQ-005.007). Archiving is the only operation that produces `archived`, for every document model.

**Custom statuses.** A document type may declare additional statuses in its configuration entry. A custom status is a front-matter value only: it causes no file move, defines no folder per status, introduces no lifecycle, and changes nothing about listing, archiving, or deleting. A record carrying a custom status remains an active record in the type folder and remains archivable. When no `default_status` is configured, a new document record starts `active`, otherwise it starts at the configured value.

**Status list invariants.** A declared status list always contains `active` and `archived`, whose meaning configuration cannot remove, rename, or redefine, and a custom status may not reuse either value. Custom statuses are available only for front-matter-backed document types. A `SingleHtmlMockup` type keeps its state in its HTML metadata with the fixed states `pending`, `approved`, and `archived`, declares no custom status, and has no `status` verb (REQ-005.008).

**The status verb.** `papyrus <document-slug> status <ID> <VALUE>` sets a record's front-matter status to a declared custom status or to `active`, changes nothing else, and refreshes `updated_date`. It never archives: the value `archived` is rejected with a validation outcome (REQ-001.004) that names `archive` as the only way to archive, and no file moves. An archived record is likewise rejected with a validation outcome that names it as archived; the command changes nothing and never restores it. No create, edit, or field option sets a status (REQ-005.011).

**Fixed configuration boundary.** Configuration cannot add, remove, or rename a category, cannot change a fixed lifecycle, and cannot change the document main statuses. Declaring document custom statuses is configuration of front-matter values only. A decision's `archived` is a status value that moves no file, while a document's `archived` is a storage location; a document is never `deprecated`.

## Acceptance Criteria

- Papyrus manages exactly three artifact categories: backlog, decision, and document.
- Tasks, milestones, and releases belong to the backlog category, decision records to the decision category, and every document type declared in the configuration to the document category.
- Each record type belongs to exactly one category, and the category owns its lifecycle.
- A document type's document model and field sequences add, remove, rename, and reshape no status and introduce no per-type lifecycle.
- Task statuses come from `statuses` and `default_status`; the milestone lifecycle is `open -> closed -> archived` and the release lifecycle is `planned -> released -> archived`, both fixed.
- Decision records use only `proposed`, `accepted`, `rejected`, `deprecated`, `superseded`, and `archived`.
- Every document type has the main status `active` or `archived`, and only these two values affect storage location.
- A document type may declare custom statuses; a custom status is a front-matter value that moves no file, creates no per-status folder, and changes no lifecycle.
- A record carrying a custom status remains an active record in the type folder, remains listed, and remains archivable and deletable.
- A declared status list always contains `active` and `archived`; configuration cannot remove, rename, or redefine them, and a custom status cannot reuse either value.
- A new document record starts `active` when no `default_status` is configured, and at the configured value otherwise.
- `status <ID> <VALUE>` sets a declared custom status or `active`, changes only the status, and refreshes `updated_date`.
- `status <ID> archived` is rejected with a validation outcome that names `archive` as the only way to archive, and no file moves.
- `status <ID> <VALUE>` on an archived record is rejected with a validation outcome that names the record as archived; nothing changes and nothing is restored.
- No create, edit, or field option sets a status.
- A `SingleHtmlMockup` type has the fixed states `pending`, `approved`, and `archived`, declares no custom status, and has no `status` verb.
- Configuration cannot add, remove, or rename a category, change a fixed lifecycle, or change the document main statuses.
- A decision's `archived` is a status value that moves no file, and a document is never described as `deprecated`.

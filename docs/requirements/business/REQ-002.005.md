# REQ-002.005 Manage Milestones

## User Story

As a project maintainer, I want to create, maintain, and archive milestones so that related tasks are organized around a delivery point and completed milestones leave the working set.

## Group

REQ-002 Backlog Management

## Criticality

Must have

## Description

`papyrus milestone create <TITLE>` creates a milestone. A milestone has a title, an optional description, an optional assignment to at most one release, repeatable acceptance criteria, and general labels and references. Its identifier uses the configured milestone prefix and the shared `id_padding` (REQ-001.005); with default configuration the first identifier is `MS-001`. Acceptance criteria are supplied with the repeatable `--ac` option on create and edit and stored as one bullet per criterion in the milestone body; `papyrus milestone view <ID> --ac` prints them alone (REQ-002.002).

**Lifecycle.** The milestone lifecycle is fixed by the backlog category (REQ-007.001): `open`, then `closed`, then `archived`. A new milestone starts `open`, and the state is stored in the front-matter `status` field (REQ-005.010). The lifecycle is not configurable, and there is no restore command.

`papyrus milestone close <ID>` changes `open` to `closed`. Closing a milestone that is not open is rejected with a validation outcome and writes nothing. `papyrus milestone archive <ID>` closes an open milestone and then sets it `archived`, moving the file to `backlog/archive/milestones/`. An archived milestone is hidden from active lists and from the Backlog board, and keeps its identifier.

**Edit.** `papyrus milestone edit <ID>` changes the title, the description, the release assignment, or the acceptance criteria. No option sets the lifecycle state apart from `close` and `archive`.

**Delete.** `papyrus milestone delete <ID>` permanently removes the milestone. Deletion asks for confirmation, and `--force` skips the prompt.

Listing and viewing milestones belong to REQ-002.002.

- A milestone is assigned to no more than one release.
- A milestone identifier uses the configured prefix and `id_padding`; with default configuration the first identifier is `MS-001`. Acceptance criteria are supplied with the repeatable `--ac` option on create and edit and stored as one bullet per criterion in the milestone body; `papyrus milestone view <ID> --ac` prints them alone (REQ-002.002).
- A new milestone starts `open`, and its state is stored in the front-matter `status` field.

- `papyrus milestone close <ID>` changes `open` to `closed`.
- Closing a milestone that is not open is rejected with a validation outcome and writes nothing.

- An archived milestone is hidden from active lists and from the Backlog board and keeps its identifier.
- `papyrus milestone edit <ID>` changes the title, description, release assignment, or acceptance criteria, and no option sets the lifecycle state apart from `close` and `archive`.
- `papyrus milestone delete <ID>` permanently removes the milestone, asks for confirmation, and `--force` skips the prompt.

# REQ-006.004 Use Front-Matter Metadata in CLI and Browser Views

## User Story

As a project contributor, I want the command line and the browser to show record information from the record metadata so that both present the same values and I do not have to look inside the file.

## Group

REQ-006 Local Web Interface

## Criticality

Must have

## Description

The command line in plain text and JSON and the browser single-record view display the same metadata values for the same record. The browser list displays the row metadata defined by the list contract (REQ-005.017, REQ-006.016) and carries no reference list. All surfaces read the record's stored metadata as defined by REQ-005.010 and project the declared fields of the record's type and role as defined by REQ-005.017; no surface derives a value from the record body when the metadata defines it, and no surface renames a stored value for display.

The command line and the browser single-record view show at least the identifier, the title, the created and updated dates, the labels, the references, and every declared field of the record's type and role. The browser list shows at least the identifier, the title, the labels, and the type's declared slots, and carries no references. A record's `status` is shown as stored, including a custom status declared for its type, and is identical in the command line and the browser.

**Browser edit form.** For a Markdown record, the form offers the fixed title control, one control per declared field whose verbs allow edit, the `labels` and `references` controls, and read-only `status`, created and updated dates. For a `formatted-record`, the form offers the fixed title control and the `references` control, with read-only `status` and dates; it has no `labels` control. `title` is not a field, and `status` is not editable because it is lifecycle- and configuration-owned (REQ-005.011). A save writes each submitted value to the field's single storage location and preserves the metadata and content the save does not change. A `formatted-record` carries no YAML front matter: its status and references are read from and written to its HTML metadata comment, its title is read from and written to the HTML `<title>` element, and the same parity applies (REQ-005.008).

## Acceptance Criteria

- CLI output and browser single-record views show the same metadata values for the same record; browser list rows show the list metadata and no references.
- The CLI and the browser single-record view show the identifier, the title, the created and updated dates, the labels, the references, and every declared field of the record's type and role.
- The browser list shows the identifier, the title, the labels, and the type's declared slots, and carries no references.
- A record's `status` is shown as stored, including a custom status, and is identical in the CLI and the browser.
- A stored value is displayed verbatim; the view does not rename or map it.
- For a Markdown record, the browser edit form offers the fixed title control, the fields whose verbs allow edit, `labels`, and `references`, with read-only `status` and dates.
- For a `formatted-record`, the browser edit form offers the fixed title control and `references`, with read-only `status` and dates, and no `labels` control.
- `title` is not edited through a field control, and `status` is not editable.
- A browser save writes each submitted value to the field's single storage location and preserves the metadata and content the save does not change.
- A `formatted-record` record's status and references are read from its HTML metadata comment, its title is read from the HTML `<title>` element, and the CLI and browser show the same values.

# REQ-001.008 Run Project Diagnostics (`papyrus check`)

## User Story

As a project maintainer, I want to diagnose corpus and configuration integrity from the command line so that problems are found and, where safe, repaired before they affect other work.

## Group

REQ-001 Project Setup and CLI Access

## Criticality

Should have

## Description

`papyrus check` is a diagnostic command. It scans the project corpus and the configuration and prints a plain report of findings. It is a tolerant surface: it loads the configuration the same tolerant way as `papyrus config` (REQ-001.002), so an invalid configuration does not block it, and it reports the configuration findings instead of failing closed.

**Checked findings.**

- Duplicate record identifiers across every managed record type: task, milestone, release, decision, and every configured document type.
- Self-referential task dependencies.
- Dependency cycles among task dependencies.
- Dangling references: any reference value that does not resolve to an existing managed record. The checked values are a task's `milestone` and dependencies, a milestone's `release`, the `references` list of every record, the values of every list-valued field restricted to record identifiers, and a decision's `superseded_by`.
- References resolve across categories: a task, milestone, release, decision, or document may reference a record of any other category, because one identifier space is used.
- A reference to an archived record resolves and is not reported: the identifier still exists, so only its location changed. A reference that names a record which was deleted, never existed, or belongs to a type that is no longer configured does not resolve and is reported.
- Unclaimed records: a Markdown file that carries managed record metadata but belongs to no configured document type, for example after a type was removed from the configuration (REQ-007.002).
- Configuration validity (REQ-007.002, REQ-007.004).

**Severity.** Each finding has a severity, `error` or `warning`. Invalid values of known attributes are errors. Unknown attributes are warnings and are ignored by commands (REQ-007.002). The plain report and the JSON form carry the same findings with their severity, kind, subject, and detail.

A configuration finding names its location by the selector path `document_types.<slug>.<path>`, using the keyed `fields[story].heading` or indexed `fields[0].heading` form and naming the field key when present. A selector path that cannot resolve uniquely — an unknown key, a missing or duplicate field key, or an out-of-range index — is itself reported as a finding rather than silently skipped.

**Invalid configuration.** When the configuration is invalid, `check` reports the configuration errors and still runs the checks that do not depend on the document-type set: duplicate identifiers among task, milestone, release, and decision records, self-referential dependencies, dependency cycles, and dangling `milestone` and `release` references. The checks that need the document-type set — duplicate identifiers across document records and unclaimed records — are skipped, and the report names them as skipped.

**Repair.** `--fix` repairs duplicate identifiers and nothing else. For a duplicated identifier the keeper is the record with the earliest valid `created_date`; a record with a missing or unparsable date ranks after every dated record; a remaining tie is broken by the lexicographically smallest project-relative path. Every other record carrying that identifier receives a new one from the regular allocator (REQ-001.005) and its file is renamed to the new identifier's stem. `--fix` does not rewrite references: the confirmation prompt lists, for each planned reassignment, every reference affected by it, naming the referring record and field.

`--fix` refuses to repair a duplicated identifier when the file stem and the front-matter `id` disagree, when the record is a group record of a grouped requirement family, or when the keeper or any other record carrying the identifier is in the import archive directory. No record of that identifier is changed and the finding remains reported.

One confirmation covers the whole repair plan, and no repair is applied unless it is confirmed or `--force` is given. `--force` without `--fix` is a usage error. When standard input is not a terminal and `--force` is absent, `--fix` writes nothing and exits with a usage error naming `--force`. Immediately before applying a repair, `--fix` re-reads the file; when it changed after the scan, the repair is skipped and reported as a repair-skipped finding while the duplicate finding stays reported. Dangling references, dependency cycles, self-references, configuration findings, and unclaimed records are never repaired.

**Outcome.** The exit status is 4 when at least one error-level finding exists, including a run in which `--fix` repaired every repairable error. A run with no error-level finding exits 0, and warnings alone do not change the exit status. The command is available only from the command line in this release, and output honours the global `--json` option (REQ-001.004).

## Acceptance Criteria

- `papyrus check` runs the documented checks and prints a plain report of findings.
- Each finding carries a severity of `error` or `warning`, a kind, the affected record or location, and a detail.
- Duplicate record identifiers are detected across task, milestone, release, decision, and every configured document type.
- Self-referential task dependencies and dependency cycles among task dependencies are detected.
- A reference value that does not resolve to an existing managed record is reported as a dangling reference.
- The checked values are a task's `milestone` and dependencies, a milestone's `release`, the `references` list of every record, the values of list-valued fields restricted to record identifiers, and a decision's `superseded_by`.
- A reference to an archived record resolves and is not reported as dangling.
- A reference to a deleted or never-existing record is reported as dangling.
- A reference to a record whose type is no longer configured is reported as dangling.
- References resolve across categories, because one identifier space is used.
- A file that carries managed record metadata but belongs to no configured document type is reported as an unclaimed record.
- Configuration validity is checked, and an invalid value of a known attribute is an error.
- An unknown attribute is a warning and does not block any command.
- A configuration finding names its location by selector path, in keyed or indexed field form, and names the field key when present.
- A selector path that cannot resolve uniquely is reported as a finding rather than skipped.
- With an invalid configuration, `check` reports the configuration errors and still runs the checks that do not need the document-type set.
- With an invalid configuration, the skipped checks are named in the report.
- `--fix` repairs duplicate identifiers and nothing else.
- For a duplicated identifier the keeper is the record with the earliest valid `created_date`, an undated record ranks after every dated record, and a remaining tie is broken by the smallest project-relative path.
- Every other record carrying the identifier receives a new identifier from the regular allocator and its file is renamed accordingly.
- `--fix` does not rewrite references, and its prompt lists every affected reference with the referring record and field.
- `--fix` refuses a duplicated identifier whose file stem and `id` disagree, whose record is a grouped requirement family group record, or where any record carrying it is in the import archive directory; no record of that identifier changes and the finding stays reported.
- One confirmation covers the whole repair plan, `--force` skips it, and `--force` without `--fix` is a usage error.
- Without a terminal and without `--force`, `--fix` writes nothing and exits with a usage error naming `--force`.
- A repair whose file changed after the scan is skipped, reported as repair-skipped, and leaves the duplicate finding reported.
- Dangling references, dependency cycles, self-references, configuration findings, and unclaimed records are never repaired.
- `--fix` does not migrate folders or rewrite any record beyond a duplicate-identifier reassignment.
- The exit status is 4 when at least one error-level finding exists, including after a successful repair, and 0 when none exists.
- Warnings alone do not change the exit status.
- `--json` renders the report, with every finding and its severity, as machine-readable JSON.
- The command is available only from the command line; no browser affordance runs it.

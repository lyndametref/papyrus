# REQ-005.010 Record Metadata in YAML Front Matter

## User Story

As a project contributor, I want every managed Markdown record to begin with structured metadata so that records can be identified, related, filtered, and displayed consistently without reading the body.

## Group

REQ-005 Project Documentation Management

## Criticality

Must have

## Description

**Scope.** Every Markdown record that Papyrus manages begins with a YAML front-matter block at byte 0, delimited by `---` lines. Front matter is authoritative for the keys it carries, and it replaces the equivalent information in the record body for records Papyrus writes. Records of a `formatted-record` type carry no front matter and keep their status and references in their HTML metadata comment, with their title in the HTML `<title>` element (REQ-005.008); prose Markdown that no document type claims is out of scope.

**General keys.** Every managed Markdown record carries `id`, `title`, `status`, `labels`, `references`, `created_date`, and `updated_date`; a member record of a `grouped-record` type also carries `group`. Papyrus writes and maintains these keys (REQ-005.011).

**Reserved keys.** The keys `id`, `title`, `status`, `labels`, `references`, `created_date`, `updated_date`, `group`, `version`, `kind`, `form`, `path`, and `metadata` are reserved. No document type declares one of them, and no field uses one as its key or as its front-matter key (REQ-007.002). `title` is fixed and is not a field; `status` is written only by the verbs that own it; `group` is the engine-owned link of a member record.

**Document keys.** Beyond the general keys, a record's front-matter keys are exactly the front-matter keys of its type's declared fields for the record's role (REQ-007.004):

- a field stored under a body heading contributes no front-matter key, and its value lives in the body;
- a field without a heading is metadata-only and stored under its key as a front-matter key; it has no body section.

A metadata-only field's front-matter key is its field key. Document keys follow field-sequence order after the general keys. An undeclared key already present on disk is preserved as stored and displayed read-only.

**Serialisation.** `created_date` and `updated_date` are quoted ISO-8601 UTC strings, for example `'2026-10-31T22:26:00Z'`. The `id` value and every reference value use the record identifier of REQ-001.005, with no second identifier space.

**Adoption and import.** Adding front matter to an existing record does not change its body (REQ-005.011). Records brought in by the one-way import are written in this format.

## Acceptance Criteria

- Every Markdown record managed by Papyrus begins with a YAML front-matter block at byte 0, delimited by `---` lines.
- Every managed Markdown record carries `id`, `title`, `status`, `labels`, `references`, `created_date`, and `updated_date`; a member record also carries `group`.
- The keys `id`, `title`, `status`, `labels`, `references`, `created_date`, `updated_date`, `group`, `version`, `kind`, `form`, `path`, and `metadata` are reserved: a document type declares none of them, and a field using one as its key or front-matter key is rejected.
- `title` is not a field, `status` is written only by its owning verbs, and `group` is the engine-owned link of a member record.
- Every front-matter key beyond the general keys is the front-matter key of a declared field of the record's role, and no other document key is written.
- A field is stored under exactly one location: a body heading or a front-matter key.
- A metadata-only field's front-matter key is its field key.
- Document keys follow field-sequence order after the general keys.
- An undeclared key already on disk is preserved as stored and displayed read-only.
- `created_date` and `updated_date` are quoted ISO-8601 UTC strings of the form `'YYYY-MM-DDTHH:MM:SSZ'`.
- The `id` value and every reference value use the record identifier, with no second identifier space.
- Records of a `formatted-record` type carry no YAML front matter and keep their status and references in the HTML metadata comment, with their title in the HTML `<title>` element.
- Prose Markdown that no document type claims is not managed.
- Adding front matter to an existing record leaves its body unchanged.
- Records brought in by the one-way import are written in this format.

# REQ-004.001 Manage Decisions

## User Story

As a project decision-maker, I want to record a decision under its own type and revise it while it is still being formed so that the record captured is the one that was settled.

## Group

REQ-004 Decision Records

## Criticality

Must have

## Description

**Create.** `papyrus <slug> create <TITLE>` creates a decision of the configured type named by the slug, from the Nygard template: a title, the decision text, the context, and the consequences. The decision text, the context, and the consequences are multiline and accept `-` to read the value from standard input. Labels and references are optional general metadata, and a reference may name any managed record, including business and non-functional requirements. A new decision starts `proposed`.

**Decision types and command family.** Decisions are configured per type in `decision_types`, a map keyed by the type slug. `init` offers both Seed types and writes the selected ones, one or both (REQ-001.006). Each entry declares a prefix and a directory, and presence in the configuration is what makes a type available: there is no `enabled` key.

The Seed contains exactly these two decision types; the criticality column is a requirement attribute of the built-in type, not a configuration key:

| Slug | Criticality | Prefix | Directory | Statuses |
|---|---|---|---|---|
| `adr` | Must have | `ADR` | `adr` | the five shared values of REQ-004.002 |
| `bdr` | Must have | `BDR` | `bdr` | the five shared values of REQ-004.002 |

The directory is the subfolder used when both types are configured; with exactly one configured type it is not applied (see Folder layout). It may be changed by editing the configuration before decisions of that type exist.

The slug is the command name, so the `adr` type is managed as `papyrus adr ...` and the `bdr` type as `papyrus bdr ...`. Each type exposes `create`, `list`, `view`, `edit`, `accept`, `reject`, `deprecate`, `supersede`, `archive`, and `delete` (the status verbs are REQ-004.002, inspection is REQ-004.003). The command selects the type, so no `--decision-type` option exists and there is no shared `decision` command family.

**Identifiers.** A decision identifier uses its type's configured prefix and the shared `id_padding` (REQ-001.005). Numbering runs per type, and the type of an existing decision is derived from its identifier prefix, not from the slug.

**Folder layout.** There is one main decision folder. When exactly one decision type is configured, that type's records are stored directly in the main folder and archived in its `archive/` subfolder; the type's directory is not applied. When two or more types are configured, each type's records are stored in the subfolder named by its directory under the main folder, and archived in that subfolder's `archive/`.

**Changing the type set.** Adding a decision type is supported only while at least two types are already configured: the new type receives its own subfolder and no existing record moves. Adding the second type to a project configured with exactly one type is not supported, because every existing decision would have to move into a subfolder; the change is rejected with a validation outcome and no file moves. Removing a configured type, and changing the prefix of a type that still has decisions, are not supported for the same reason.

**Update.** `papyrus <slug> edit <ID>` changes the title, the decision text, the context, the consequences, the labels, or the references. An edit is allowed only while the decision status is `proposed`; once the decision has left `proposed`, its content, its title, its labels, and its references are frozen and an edit is rejected with a validation outcome and writes nothing. Status changes are not part of an edit; they belong to REQ-004.002.

**Delete.** `papyrus <slug> delete <ID>` permanently removes a decision, and is allowed only while the status is `proposed`. Deletion asks for confirmation, and `--force` skips the prompt. A decision that has left `proposed` cannot be deleted; it is archived instead (REQ-004.002).

**Dates.** A decision carries two dates. Its creation date is when the decision was first created; it is written at creation, never changes afterwards, and is what the views show as the decision's date. Its update date is when its status was last changed; a status verb refreshes it, while a content edit of a `proposed` decision does not (REQ-005.011).

**Status storage.** The decision status stays in the `## Status` section of the document body (REQ-005.010).

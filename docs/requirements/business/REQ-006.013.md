# REQ-006.013 Present the Backlog as a Per-Milestone Kanban Board

## User Story

As a project contributor, I want the browser Backlog view to show tasks as a kanban board inside each milestone, with the release boundary marked and the lifecycle state visible, so that I can see how work is distributed and clean up finished work from one place.

## Group

REQ-006 Search and Local Web Interface

## Criticality

Should have

## Description

**Board structure.** The Backlog view keeps milestones as expandable and collapsible sections. Inside an expanded milestone its tasks appear as a kanban board: one column per task status, laid out horizontally, with columns following the configured task status list exactly and in configured order. A status with no task keeps its column visible. Milestones that belong to a release appear under that release; milestones that belong to no release are grouped before the first release, and each release boundary is marked by a bold separator naming the release, so the boundary does not depend on colour. Tasks that belong to no milestone appear in their own expandable section after all milestone sections. Cards are ordered by ascending task identifier within a column and link to the task record view.

**Ordering.** Milestones are ordered by the lowest ordinal among the non-archived tasks assigned to them, ascending; a milestone with no such task comes after every milestone that has one, ordered by milestone identifier ascending; equal lowest ordinals are ordered by milestone identifier ascending. The same rule applies inside a release and in the no-release group. Releases are ordered by the lowest ordinal among the non-archived tasks in their milestones, ascending; a release with no such task comes last, ordered by release identifier ascending; equal lowest ordinals are ordered by release identifier ascending. The order is recomputed from current record data on each render.

**Lifecycle markers.** A lifecycle marker is placed immediately before each milestone and release title, in addition to the record identifier: a ring marker for an open milestone or a planned release, and a check marker for a closed milestone or a released release. The marker reflects the stored lifecycle state and changes when that state changes and the view is reloaded. Archived milestones and archived releases are not shown and carry no marker.

**Task status change.** A task's status is changed by dragging its card into another status column, or with an equivalent status control on the card that needs no dragging. Either action persists the status immediately; the board is not a staging area. A change that cannot be persisted leaves the card in its original column and reports the failure. A status change alters only the status value and preserves every other task field.

**Task cleanup.** The final configured task status column of each milestone board offers a "Clean up all" action. The final configured status is the last entry of the configured task status list. Activating it shows a warning listing the identifiers of the affected tasks and requires confirmation; on cancel nothing is archived. On confirmation each task in that column for the current milestone is archived independently: a failure is reported for that task and does not abort the others, and archived tasks leave the board. The action never acts project-wide and has no command-line equivalent.

**Milestone and release cleanup.** A cleanup control appears immediately after the title of every closed milestone and of every released release that contains at least one closed milestone; a released release with no closed milestone has none. Activating it shows a confirmation listing the identifiers of the records that will be archived, and cancelling archives nothing. For a closed milestone, confirmation archives that milestone. For a released release, confirmation archives each closed milestone contained in it, one by one, and leaves the release itself visible and released. If archiving one record fails, the failure is reported for that record, the remaining records are still archived, and the failed record stays visible.

Presentation details not fixed here — card contents beyond the identifier and title, column widths, separator styling, and control placement — are design decisions. Archived tasks appear on no board.

## Acceptance Criteria

- The Backlog view keeps milestones as expandable and collapsible sections, and an expanded milestone shows its tasks as a kanban board with one column per task status.
- Columns follow all configured task statuses in configured order and stay visible when empty.
- Each release boundary is marked by a bold separator naming the release and does not rely on colour.
- Milestones assigned to a release appear under it, and milestones assigned to no release appear before the first release.
- Tasks that belong to no milestone appear in their own expandable section after all milestone sections.
- Cards are ordered by ascending task identifier within a column, and each card links to the task record view.
- Milestones are ordered by the lowest ordinal of their non-archived tasks, ascending; a milestone with no such task comes last, by identifier; ties are ordered by identifier.
- Releases are ordered by the lowest ordinal of the non-archived tasks in their milestones, ascending; a release with no such task comes last, by identifier; ties are ordered by identifier.
- The order is recomputed from current record data on each render, and changing a task ordinal moves its milestone and release on reload.
- A ring marker precedes the title of every open milestone and every planned release, and a check marker precedes the title of every closed milestone and every released release.
- The marker appears in addition to the record identifier, reflects the stored state, and changes after the state changes and the view is reloaded.
- Archived milestones and archived releases are not shown and carry no marker.
- A task's status is changed by dragging its card into another status column, or with an equivalent control on the card.
- A status change is persisted immediately and is still shown after reload, and it changes only the status value.
- A status change that cannot be persisted leaves the card in its original column and reports the failure.
- The final configured task status column of each milestone board offers "Clean up all".
- "Clean up all" shows a warning listing the affected task identifiers, requires confirmation, and archives only the current milestone's tasks in that column.
- On confirmation every listed task is archived and leaves the board; a failure is reported per task and does not abort the others; on cancel nothing is archived.
- "Clean up all" has no command-line equivalent.
- Each closed milestone and each released release containing at least one closed milestone shows a cleanup control immediately after its title, and a released release with no closed milestone shows none.
- A cleanup confirmation lists the identifiers of the records that will be archived, and cancelling archives nothing.
- Confirming a milestone cleanup archives that milestone and removes it from the view.
- Confirming a release cleanup archives each closed milestone in that release, removes them from the view, and leaves the release visible and released.
- A release cleanup never archives the release itself.
- A cleanup failure is reported for that record, the remaining records are still archived, and the failed record stays visible.
- Milestone and release cleanup controls have no command-line equivalent and change no lifecycle rule.
- Archived tasks appear on no board.

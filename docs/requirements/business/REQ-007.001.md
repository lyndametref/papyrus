# REQ-007.001 Organize Artifacts into Three Categories

## User Story

As a project contributor, I want every artifact to belong to a known category so that I know which lifecycle applies and what configuration can change.

## Group

REQ-007 Artifact Categories and Config-Defined Document Types

## Criticality

Must have

## Description

Papyrus manages exactly three artifact categories:

- **backlog** — tasks, milestones, and releases.
- **decision** — decision records.
- **document** — every document type declared under `document_types`, including the default entries and any entry added by the user.

Each record type belongs to exactly one category.

**Content model independence.** A document type's content model — its `DocumentModel`, its role field sets, its field sequence, and its field options — describes record content and where that content is stored only. It adds, removes, renames, and reshapes no status, changes no status storage location, and introduces no per-type lifecycle (REQ-007.004). The status model is a property of the artifact category, so every document type follows it unchanged whatever its model and whatever fields it declares.

Status models differ by category. Task statuses are configurable through `statuses` and `default_status` (REQ-001.002). Within the backlog category, the milestone and release lifecycles are fixed: a milestone is `open`, then `closed`, then `archived`, and a release is `planned` then `released`. Decision records use the fixed Nygard statuses `proposed`, `accepted`, `rejected`, `deprecated`, and `superseded` (REQ-004.001). Document types have a **main status** plus optional **custom statuses**, described below.

**Main status.** Every document type has the main status `active` or `archived`, and these are the only statuses that affect storage location. An `active` record is stored in the document type's configured folder; an `archived` record is stored in the `archived/` subfolder of that folder and carries `status: archived` (REQ-005.007). A record's status is exactly `active`, a declared custom status, or `archived`; no other value is valid. For every document model, `archive` is the only operation that produces the `archived` state, including the HTML metadata state of a UI mockup (REQ-005.008).

**Custom statuses.** A document type may declare additional statuses in `document_types.<slug>.statuses` (REQ-007.002), optionally with a configured initial value in `document_types.<slug>.default_status`. Custom statuses are front-matter values only: they cause no file move, define no folder per status, introduce no new lifecycle, and change nothing about which records are listed, whether a record can be archived or deleted, or where a record is stored. A record carrying a custom status is an active record in the type folder and remains archivable. When no `default_status` is configured, a new document record starts `active`.

**Status list invariants.** Every document type's declared status list includes `active` and `archived`. Those two values are fixed: configuration cannot remove, rename, or redefine them, and a custom status may not reuse either value. Custom statuses are available only for front-matter-backed document types. A `SingleHtmlMockup` type keeps its state in HTML metadata with the fixed states `pending`, `approved`, and `archived` (REQ-005.008), declares no custom status, and has no `status` verb; `archive` is its only path to `archived`.

**Setting a status from the CLI.** A document record's status changes only through the `status` and `archive` verbs: creation writes the initial status (the configured `default_status`, or `active` when none is configured), and no create, edit, or field option sets it (REQ-005.011). `papyrus <document-slug> status <id> <value>` sets a record's front-matter `status` to a declared custom status or to `active`. It changes only the status value and refreshes `updated_date`. This command never archives: the value `archived` is rejected with a validation outcome (exit code 4, REQ-001.004) that names `archive` as the only way to archive a record, and no file is moved. An archived record is likewise rejected with a validation outcome (exit code 4) that names the record as archived; `status` changes nothing on it and never moves it back. UI mockups have no `status` verb and no custom statuses: their lifecycle is governed by REQ-005.008, and `archive` is their only path to `archived`.

**Archiving a record with a custom status.** Archiving such a record sets `status` to `archived` and moves the file into the `archived/` subfolder (REQ-005.007). The previous custom status is not retained: no front-matter field or metadata stores the value that the record had before archiving, and documents have no restore command. Archiving remains the only path to `archived` for every document model: no status verb, configuration value, field option, or content field produces that state.

Configuration cannot add, remove, or rename a category, and cannot change a fixed lifecycle (milestone, release, or decision) or the document main statuses. Declaring document custom statuses is configuration of front-matter values, not a change to those fixed lifecycles.

The decision status `deprecated` and the document state `archived` are different terms for different categories: a decision is never `archived`, and a document is never `deprecated`.

## Acceptance Criteria

- Papyrus manages exactly three artifact categories: backlog, decision, and document.
- Tasks, milestones, and releases belong to the backlog category; decision records belong to the decision category; every document type declared under `document_types` belongs to the document category.
- Each record type belongs to exactly one category.
- The content model does not alter the status model: a type's `DocumentModel`, role field sets, field sequence, and field options add, remove, rename, and reshape no status, change no status storage location, and introduce no per-type lifecycle (REQ-007.004).
- Task statuses are configurable through `statuses` and `default_status` (REQ-001.002); document types may additionally declare custom statuses through `document_types.<slug>.statuses` and an optional `document_types.<slug>.default_status`.
- The milestone lifecycle is fixed to `open -> closed -> archived` and the release lifecycle is fixed to `planned -> released`; neither is affected by any `statuses` or `default_status` configuration.
- Decision records use only `proposed`, `accepted`, `rejected`, `deprecated`, and `superseded`.
- Every document type has the main status `active` or `archived`; an active record is stored in the type folder and an archived record is stored in that folder's `archived/` subfolder with `status: archived` (REQ-005.007).
- A document record's status is exactly `active`, a declared custom status, or `archived`, and no other value is valid.
- A document record's status changes only through the `status` and `archive` verbs; creation writes the initial status (`default_status` or `active`), and no create, edit, or field option sets a status (REQ-005.011).
- A document type's declared statuses always include `active` and `archived`; configuration cannot remove, rename, or redefine them, and a custom status cannot reuse either value.
- A custom status is a front-matter value only: setting it moves no file and creates no per-status folder.
- A record carrying a custom status remains in the active storage location, is still listed, and can still be archived and deleted.
- A new document record starts `active` when no `default_status` is configured, and starts at the configured `default_status` when one is.
- `papyrus <document-slug> status <id> <value>` sets a declared custom status or `active` in the front matter, changes only the status, and refreshes `updated_date`.
- `papyrus <document-slug> status <id> archived` is rejected with a validation outcome (exit code 4) that names `archive` as the only way to archive, and no file is moved.
- `papyrus <document-slug> status <id> <value>` on an archived record is rejected with a validation outcome (exit code 4) that names the record as archived; no status change and no file move occur.
- Archiving a record that carries a custom status sets `status: archived`, moves the file to the `archived/` subfolder, and does not retain the previous custom status value anywhere.
- Archiving is the only path to `archived` for every document model: no status verb, configuration value, field option, or content field produces that state.
- A `SingleHtmlMockup` type has the fixed states `pending`, `approved`, and `archived`, declares no custom status, and has no `status` verb; `archive` is its only path to `archived` (REQ-005.008).
- Configuration cannot add, remove, or rename a category and cannot change a fixed lifecycle or the document main statuses.
- A decision is never described as archived, and a document is never described as deprecated.

# ADR-042 Document engine CLI surface rulings

## Status
accepted
## Decision
These rulings settle the architectural questions raised during MS-034 refinement. They are normative for the descriptor-driven document engine and apply uniformly to every document type. Only the clauses named here change; every other accepted decision remains in force.

1. **The `audit_type` default is seed data, not an engine rule.** The `audit` seed entry carries a `field_defaults` map with `audit_type: security`. `SeedDocumentType` gains a `field_defaults` slice, empty for every other seed type, and the resolved descriptor carries the same map. On `create`, when a field that has a seed default is absent, the engine writes the default through the ordinary `PatchOp` path; on `edit` an absent field stays absent. `field_defaults` is not a key of `FieldSpec`, not a configuration key, and not accepted in a project entry; a user-defined type has no field defaults. This mirrors `default_status` as a seed presentation fact and keeps the nine-key `FieldSpec` unchanged. The seed table of ADR-036 decision 29 must record `field_defaults: { audit_type: security }` on `audit`, and no other type gains a default. No slug literal in the CLI, engine, or browser supplies the value.

2. **Verb about lines are engine-generated generic text.** The about line of every verb is generated by the engine from the document model and the field sequence; per-type verb about text is not preserved and not frozen. `TASK-260` attributes every resulting help diff to this ruling. No seed field carries per-type verb prose and no per-type help module returns (ADR-036 decision 8). The frozen help surface is narrowed to the root about line, `Manage <slug> documents.`, each enabled type's help line, the type order, and the verb listing of `papyrus <slug> --help`; per-verb about text is generated prose, like per-option prose. ADR-0016 decision 7 and TECH-070 section 6 are amended accordingly.

3. **Mockup status stays on the CLI edit verb.** For `SingleHtmlMockup`, the CLI `edit` verb keeps `--status` and `--superseded-by` exactly as today; this is behaviour preservation under MS-034 AC-1. The browser edit form continues to offer only the title, `specs`, and `refs` controls (ADR-039 decision 21), and the `status` verb remains absent for this model. This resolves the REQ-05.008 open question for the CLI: approval is recorded with `edit --status approved`, while `archive` and `supersede` remain the only writers of `archived`. The REQ-05.008 open-question wording needs a Phase 2 alignment by `requirements-engineer`; this record does not edit the requirement.

4. **Help and list order stay in effective configuration map order.** Enabled document types are listed in effective `document_types` map order, which is slug order, not seed `order`. The current top-level help and list order is the required order; seed `order` remains presentation data and never reorders commands or lists. ADR-0016 decision 7's claim that seed order reproduces the current order and TECH-070 section 2's seed-order sentence are corrected by this ruling. REQ-07.003's frozen-order clause is satisfied by keeping the current order; its "seed `order`" sentence is contradicted and is owned by `requirements-engineer` for Phase 2 alignment.

5. **Configuration reads resolve field leaves; configuration writes do not edit them.** `config get` and `config list` accept keyed and numeric field selector paths and resolve them to effective leaves. `config set` and `config unset` reject every selector inside a `fields`, `group.fields`, or `member.fields` sequence as a file-edit-only change: they never add, remove, reorder, or edit a field property. This follows ADR-0019 decision 10 as amended and ADR-0024's amendment of 2026-11-20. MS-034 AC-3's "get/set/unset agree" and field-selector wording must be narrowed to this split by the planner.

6. **Only `statuses` keeps comma syntax on set and unset.** `document_types.<slug>.statuses` and the top-level task `statuses` are the only list-valued keys on `config set` and `config unset`, with the comma syntax and flow-sequence storage of ADR-0024. `api_aliases` and `slots` are declarative file data: they are not `config set` targets and never use comma syntax, `slots` being a sequence of mappings. `fields` and role field sequences are never comma-set. MS-034 AC-3's "flat lists (statuses, api_aliases, slots)" wording must be narrowed to `statuses` only by the planner.
## Context
MS-034 refinement raised eight decisions across TASK-255 to TASK-261. Six are architectural and block implementation because the accepted sources either leave the behaviour unstated or contradict the current implementation:

- the `audit_type` default has no home in the nine-key `FieldSpec`, yet REQ-05.006 requires `security` when `--audit-type` is omitted;
- frozen per-type verb about lines (ADR-0016 decision 7, TECH-070 section 6) conflict with the ban on per-type help modules (ADR-036 decision 8);
- the REQ-05.008 open question asks whether approval is available on the CLI mockup edit verb while the browser form already has no status control;
- TECH-070 section 2 and ADR-0016 decision 7 claim seed `order`, but the delivered help and list order is effective map order, and REQ-07.003 freezes the current order;
- MS-034 AC-3 asks `config set` and `config unset` to edit field properties, which contradicts ADR-0019 decision 10 as amended and ADR-0024's amendment;
- MS-034 AC-3 groups `api_aliases` and `slots` with `statuses` as comma-separated lists, although only status lists can be expressed as a scalar list.

The other two refinements are not architectural and stay with the planner: the browser dependency on the eight document `edit::*_ops` builders before they can be deleted, and the stale RC-package acceptance criteria in TASK-261.

Forces: behaviour preservation under MS-034 AC-1; one engine parameterized by the descriptor with no per-type module, slug literal, or per-type help; the nine-key `FieldSpec` and the seed table as the only built-in definition; the single `PatchOp` write path; accepted configuration, decision, and requirement sources that cannot all be satisfied literally; and implementation readiness without reopening the requirement or Technical specification bodies beyond the named dated notes.

Alternatives considered:

| Option | Outcome | Reason |
|---|---|---|
| Put the `audit_type` default in an engine match on the `audit` slug | Rejected | A slug literal selects record data and contradicts ADR-036 downstream constraint 1. |
| Add a `default` key to `FieldSpec` | Rejected | Changes the nine-key field vocabulary in ADR-036 decision 11 and exposes defaults to project configuration. |
| Keep per-type verb about text in a new seed field | Rejected | Per-type prose in the seed is still per-type help data and defeats the one-engine rule; a generic derivation is sufficient. |
| Remove CLI `--status` for mockups to match the browser form | Rejected | Violates MS-034 AC-1 behaviour preservation and leaves no CLI path to `approved`. |
| Reorder help and lists to seed `order` | Rejected | Changes the frozen current output and contradicts the delivered configuration-map order. |
| Allow `config set` and `config unset` on field leaves | Rejected | Contradicts ADR-0019 decision 10 as amended, ADR-0024's amendment, and the file-edit-only field rule. |
| Classify `api_aliases` and `slots` as list-valued keys | Rejected | A comma-separated scalar cannot express a sequence of mappings, and the two are declarative file data. |
## Consequences
**Positive:**

- The `audit_type` default becomes seed data read by the engine, so neither the CLI nor the browser hard-codes a slug or a type fact; `FieldSpec` and project configuration stay unchanged.
- Verb about lines are generated uniformly, so the last per-type help prose cannot survive the module deletion and TASK-260 can attribute every help diff.
- CLI mockup behaviour is preserved exactly, the browser form keeps its narrower surface, and the REQ-05.008 open question is answered for the CLI.
- Help and list order stay stable, so the frozen golden does not change for ordering.
- Configuration reads and writes have one predictable boundary: reads resolve every effective leaf; writes edit only scalar leaves and status lists.
- Only `statuses` carries comma syntax, matching the only list-valued keys that a scalar comma form can express.

**Negative:**

- `field_defaults` is new seed data outside `FieldSpec`; the seed table and the resolved descriptor must carry it, and a type cannot declare its own default through configuration.
- Per-verb about text changes for every document type, so TASK-260's golden diff is larger; this is accepted generated prose, not a regression.
- `--status` and `--superseded-by` remain on the CLI mockup edit verb while the browser form has no status control; the two surfaces stay intentionally asymmetric.
- Seed `order` is presentation-only and no longer governs command or list order, so the requirement sentence that says otherwise remains stale until Phase 2.
- `config set` and `config unset` remain unable to edit a field property; a user must edit the YAML file for any field-sequence change.

**Risks and mitigations:**

- *Default leaks into the engine as a slug check*: the resolved descriptor carries `field_defaults`; a no-drift check asserts no document slug literal selects a default.
- *Help diff treated as a regression*: TASK-260 attributes every per-verb about-line change to ruling 2 and updates the expected-deltas record.
- *Order drift*: the help golden keeps the current configuration-map order, and a test asserts seed `order` does not reorder the tree.
- *Config write bypass*: `config set`/`unset` reject field selectors with a selector-path diagnostic; `config get`/`list` still resolve them.
- *Requirement and milestone drift*: REQ-05.008 and REQ-07.003 wording and MS-034 AC-3 are reported to the orchestrator for Phase 2 and planner alignment; this record does not edit them.

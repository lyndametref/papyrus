# REQ-001.002 Read and Edit Project Configuration

## User Story

As a project maintainer, I want to inspect and change configuration values so that Papyrus uses settings appropriate to my project.

## Group

REQ-001 Project Setup and CLI Access

## Criticality

Must have

## Description

The user can list the effective configuration, read one value, set one value, and unset one key so that its default applies again. Keys use dotted notation, and a document type is addressed beneath `document_types.<slug>` (REQ-007.002).

**Selector paths.** A document-type leaf is addressed as `document_types.<slug>.<path>`. A field sequence element is addressed by key, as in `document_types.req.member.fields[story].heading`, or by zero-based index, as in `document_types.req.group.fields[0].required`; both forms resolve to the same element. `config get` and `config set` accept one selector. `config list` prints the effective configuration with every default resolved, each leaf addressed by its selector path and field properties addressed by the key selector. A selector that does not resolve to a leaf — an unknown key, a keyed selector matching no unique field, or an out-of-range index — is rejected with a validation outcome.

**Set and unset.** `config set <selector> <value>` changes a declared entry and validates the resulting configuration before writing it. Adding or removing a document type, and adding, removing, or reordering a field, is a configuration file edit. `config unset` of a scalar removes the key so its default applies again; `config unset` of a flat collection (`statuses`, `api_aliases`, `slots`) removes it so the collection default applies. For a document type the default is the model-level default of REQ-007.002, never a value from a built-in table.

**Value shapes.** A scalar key is parsed as a YAML scalar. A list-valued key — the task `statuses`, a document type's `statuses`, `api_aliases`, and `slots` — accepts a comma-separated value, for example `papyrus config set document_types.req.statuses active,archived`, and writes it as a YAML flow sequence. A comma is always a separator with no escape form, and an empty value for a list-valued key is rejected rather than written. `fields` and the role field sequences are sequences of mappings and are never written from a comma-separated value.

**Unknown attributes.** An unknown attribute in the configuration file is accepted and ignored with one warning (REQ-007.002); it is never reported as an error by `config` commands. Selecting an unknown attribute, however, is an unresolvable selector and is rejected.

**Folder change.** Changing a folder with `papyrus config set` — a document type's `directory`, or `backlog_directory`, `decision_directory`, or `doc_directory` — moves the entire content of the original folder to the new one: every file and subfolder, not only managed records. The move happens during the `set` command, is a move rather than a copy, and is atomic: if any entry cannot be moved, for example because an entry with the same relative path exists at the destination, nothing is moved, both folders keep their content, the new value is not persisted, and the command reports a conflict (REQ-001.004).

**Validation and repair.** The effective configuration is validated at load (REQ-007.002). While it is invalid, every command fails closed with a validation outcome (REQ-001.004), except the repair surfaces: `config get|set|unset|list` load tolerantly, validate the configuration that would result from the requested change, and refuse a write that would still be invalid; `init --force` replaces the file with the generated configuration; `check` reports the findings and runs the checks that do not depend on the document-type set (REQ-001.008). A broken configuration is therefore always repairable through Papyrus.

## Acceptance Criteria

- `papyrus config list` prints the effective configuration with every default resolved, addressing each leaf by its selector path and field properties by the key selector.
- `papyrus config get <selector>` prints that leaf's effective value, and `get` and `set` accept exactly one selector.
- A document-type leaf is addressed with dotted notation beneath `document_types.<slug>`, and the `group` and `member` blocks and `fields` sequence are nested data addressed by selector paths.
- A field sequence element resolves both by key and by zero-based index to the same element.
- A selector that does not resolve to a leaf is rejected with a validation outcome.
- `config set` changes a declared entry, validates the result, and writes it; adding or removing a document type, or changing a field sequence, is a configuration file edit.
- `config unset` of a scalar removes the key so its default applies, and of a flat collection so the collection default applies.
- A document-type default is the model-level default of REQ-007.002, never a value from a built-in table.
- A scalar value is persisted as a YAML scalar, and a comma inside a scalar is part of it.
- A list-valued key accepts a comma-separated value and stores it as a flow sequence with the same values in the same order.
- Commas in a list value have no escape form, and an empty value for a list-valued key is rejected.
- `fields` and the role field sequences are never written from a comma-separated value.
- An unknown attribute is accepted, ignored with one warning, and not reported as an error by `config` commands; selecting it is rejected as an unresolvable selector.
- Changing a folder moves every file and subfolder of the original folder during the `set` command, and the original folder keeps nothing that was moved.
- A folder move that cannot complete reports a conflict, persists no change, and leaves both folders unchanged.
- While the configuration is invalid, every command fails closed with a validation outcome except `config get|set|unset|list`, `init --force`, and `check`.
- `config` commands load an invalid configuration, validate the result of the requested change, and refuse a write that would still be invalid.
- `init --force` can replace an invalid configuration with the generated configuration.
- `papyrus check` loads an invalid configuration, reports the findings, and runs the checks that do not depend on the document-type set.
- The configured task statuses are unique, and the configured default task status is one of them.

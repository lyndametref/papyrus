# REQ-005.009 Manage Technical Specifications

> **Deprecated.** Superseded by REQ-005.015. This record mixed the technical specification activity with the document-model requirement that now covers it; it is retained only for traceability.

## User Story

As a project contributor, I want technical specifications to be recognized as a project documentation type so that technical documentation can be referenced by tasks and can reference non-functional requirements.

## Group

REQ-005 Project Documentation Management

## Criticality

Must have

## Description

`tech-spec` is a `SingleMarkdown` document type (REQ-007.004): one record per plain ID `TECH-<n>`, stored under the `technical/` directory below `doc_directory` by default, with a Markdown body.

**Declared field.** The type's field set is seed data and is not declared in project configuration (ADR-036 decisions 26 and 29): the single field `description` is stored under the heading `## Description`. The field is optional and body-only — it may be omitted or cleared, and its value lives in the body under the declared heading, never in YAML front matter. The record title is required on create under the uniform title contract and is not a field (RE-010 D13, REQ-005.010). No other field belongs to this type; adding or changing a field is a configuration file edit (REQ-007.002).

**Title and options.** `papyrus tech-spec create <TITLE> --description <TEXT>` creates a specification; `--title` is accepted on create and edit. The title is single-line and non-empty, is required on create, and can never be cleared by an edit; supplying both the positional `TITLE` and `--title` is rejected and writes nothing (REQ-007.003). `--description` is the field option and accepts `-` to read the value from standard input; `--editor` edits the description in an external editor. Labels and references remain general metadata supplied through `--label` and `--reference` (REQ-005.010). No create or edit option sets `status` (REQ-005.011).

**IDs and paths.** The ID uses the `TECH` prefix (for example `TECH-001`), padded to the configured `id_padding` (REQ-001.005). Technical specifications follow the same input sanitization and project-directory path boundary as other document types (NFR-002.002, NFR-004.002).

**References.** A task may reference zero or more technical specifications (REQ-002.001), and a technical specification may reference non-functional requirements. Reference visibility for this type is `visible`, so a list row renders its reference list (ADR-036 decision 29).

**Lifecycle.** Specifications carry front-matter `status` with the value `active`, a declared custom status, or `archived`; only the `status` and `archive` verbs write it (REQ-007.001). Archiving hides a specification from lists, search, and the web UI, moves it to the type's `archived/` subfolder, and preserves its ID (REQ-005.007). Deleting a specification permanently removes it under the document deletion rules (REQ-005.007).

## Acceptance Criteria

- `tech-spec` is a `SingleMarkdown` document type whose model comes from the seed table, with one record per plain ID `TECH-<n>` (REQ-007.004).
- The type declares exactly one field, `description`, stored under the heading `## Description`.
- `description` is optional: a create that supplies only a title succeeds, and an edit may supply or clear it.
- `description` declares no front-matter key, so its value is stored only in the body under `## Description`.
- `papyrus tech-spec create <TITLE> --description <TEXT>` creates a specification with the first positional `TITLE`, and `--title` is accepted on create and edit.
- A create without a title, with an empty title, with a multi-line title, or with both the positional `TITLE` and `--title` is rejected and writes no file; an edit cannot clear the title.
- `--description` is the field option and accepts `-` to read the value from standard input; `--editor` edits the description.
- No create or edit option sets `status`, and labels and references are supplied through `--label` and `--reference`.
- Technical specifications are stored under `technical/` (below `doc_directory`) with IDs using the `TECH` prefix, padded to `id_padding` digits.
- Technical specifications can be listed, viewed, and edited for title and description, including via `--editor`.
- A task may reference zero or more technical specifications (REQ-002.001), and a technical specification may reference non-functional requirements.
- A list row for a `tech-spec` record renders its reference list because the seed reference visibility of the type is `visible`.
- Archiving a technical specification hides it from lists, search, and the web UI, moves it to `archived/`, and preserves its ID; no restore command exists (REQ-005.007).
- Technical specifications follow the same input sanitization and project-directory path boundary as other document types.
- A `tech-spec` record carries front-matter `status`, written only by the `status` and `archive` verbs (REQ-007.001, REQ-005.011).

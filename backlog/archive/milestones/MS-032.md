## Description
Internal checkpoint of one deliverable: baseline only, no product behavior change.

Goal: freeze observable behavior and performance before refactoring so every later milestone can prove equivalence. Builds on MS-031.

Known measurements to reproduce: inventory / 14.2 s and /doc/REQ-07.001 1.8 s on 382 active records. Root cause is migrate::ensure_front_matter calling managed_descriptor/load_cfg_for per record, which reads and parses config and builds ArtifactRegistry at least twice per record; load_record resolving titles through resolve_id rescans descriptor directories making index construction O(n^2); per-request ServerState::config() reloads config; no index cache.

Baseline sampling amendment (planner):
The NFR-007 protocol of 10 warm-up + 100 measured requests per route is a post-refactor target. On the measured host the pre-refactor engine needs about 1.04 s per inventory request at 100 records, 11.36 s at 382 and 74.37 s at 1,000, and 23.90 s per grouped-member view at 1,000 records; the full protocol over 11 routes, 2 runs and 3 profiles would run for roughly 15 to 16 hours. That latency is the defect MS-036 removes, so the baseline uses a reduced-sample protocol instead of the full one:
- Band A, route p50 below 1 s: 10 warm-up + 100 measured requests, the unchanged NFR-007 protocol.
- Band B, route p50 at or above 1 s: 2 warm-up + 20 measured requests.
- Band selection is deterministic: the first five measured samples of run A decide the band per route and profile, they count toward the total, and run B reuses the same band and counts.
- Every route and profile records its band, warm-up count and measured count, with the reason for any count below the full protocol: pre-refactor per-request latency, not measurement uncertainty.
- p50 and p95 stay mandatory. A p95 from fewer than 100 samples is a baseline-only figure and is never compared against the NFR-007 thresholds.
MS-036 keeps the full NFR-007 protocol for the post-refactor measurement (NFR-007.001 and NFR-007.002 measurement method: 10 warm-up + 100 measured requests per route), so the baseline deviation never enters the acceptance comparison. NFR-007.001 to NFR-007.003 are unchanged.

Acceptance criteria:
AC-1 A benchmark harness measures inventory and view/edit at 100, 382 and 1,000 records on recorded reference hardware and reports p50 and p95 per route and profile, using the full NFR-007 sample count where per-request latency allows it and the reduced-sample protocol of AC-8 where it does not.
AC-2 Characterization fixtures cover record files, JSON payloads, rendered HTML, and HTTP status codes for every document type and every document route.
AC-3 The renderer inventory is corrected and recorded with file paths: 9 conflict-page renderers and 5 not-found pages.
AC-4 Pre-refactor baseline numbers are recorded, including the 14.2 s and 1.8 s figures at 382 active records, each with the corpus, the sample counts actually used, and the reason for any count below the full NFR-007 protocol.
AC-5 A CLI help snapshot exists for every document command.
AC-6 Current create/edit bytes are captured per document type, including title handling and glossary --term.
AC-7 No production behavior changes; the suite is green at the end of the milestone.
AC-8 The reduced-sample protocol is documented per route and profile: the baseline summary records the band, warm-up count and measured count used, states that any count below 10 warm-up + 100 measured is caused by pre-refactor per-request latency and not measurement uncertainty, and reports every p95 from fewer than 100 samples as baseline-only rather than as an NFR-007 comparison.
AC-9 The baseline summary states that the post-refactor measurement in MS-036 uses the full NFR-007 protocol of 10 warm-up + 100 measured requests per route, so the reduced baseline sample count is never used in the acceptance comparison, and that NFR-007.001 to NFR-007.003 are unchanged.

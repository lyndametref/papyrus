R19. "config set" cannot add a document type any more
    Severity: high (cross-group conflict with REQ-001.002)
    REQ-007.002 now says adding a document type is a configuration file edit and
    "config set" changes a declared entry. REQ-001.002 still says "config set
    document_types.<slug>.<path>" materializes an absent entry. Under a
    configuration-only model a materialized entry would lack "prefix" and
    "directory" and could not validate, so REQ-001.002 must adopt the same rule.

R20. "papyrus check" must report files of unconfigured types
    Severity: medium (implementation gap)
    REQ-007.002 requires a finding for every file that carries managed record front
    matter but belongs to no configured document type. No check rule exists yet, and
    the finding needs a stable diagnostic code. It must not fire on prose Markdown
    (REQ-005.010) or on the former "deprecated/" folders (REQ-005.007).

R21. Field semantics split across two requirements
    Severity: low
    REQ-007.002 owns the configuration syntax and validation of field items;
    REQ-007.004 owns their semantics (storage locations, required and clearing
    rules, sequence order). Deliberate, but a change to one must be mirrored in the
    other.

R22. Two behaviours newly required, not yet implemented
    Severity: medium
    a) Shorthand dispatch: "papyrus <slug> <ID>" means view when no verb is given
       and the token is an identifier of the type.
    b) Renaming a slug is configuration-only, with no migration; nothing warns the
       user that the former records become unmanaged.

R23. ADR amendments still outstanding for this group
    Severity: high
    ADR-0016 (dispatch from the seed), ADR-0019 (fail-closed unknown keys, enabled),
    ADR-0024 (list-valued keys), ADR-036 decisions 28-34 (seed fill, overlay,
    validation, seed-only models).

GROUP REQ-001 — Project Setup and CLI Access
(reviewed, changes applied)
====================================================================

State after review: 7 active atomics, 1 deprecation. 8,242 -> 5,416 words (-34%).
Active: .001 .002 .003 .004 .005 .006 .008. Archived: .007.

Resolved by the rewrite: init writes the selected Seed entries (R2a); "config set"
cannot add a type (R2e, R19); `enabled` and seed-minimal entries removed; the false
"milestones are never archived" statement fixed in .005; the seed-only identifier
shape replaced by the configured model; `id_padding` now lives once, in .005.

R41. Exit status now depends on finding severity
    Severity: high (behaviour change)
    REQ-001.008 states that an error-level finding gives exit 4 while warnings alone
    give 0. The previous rule was "exit 4 whenever any finding exists". Commands,
    business rules and test cases that assume any finding fails must adopt severity.

R42. Deliberate deviation from D2 on the "deprecated/" sentence
    Severity: medium
    D2 asked to drop the inert `deprecated/` sentence from REQ-005.007. It was kept:
    without it, files in such a folder have no defined behaviour (they are neither
    archived nor unmanaged). Only the legacy conflict checks and `--fix` legacy
    refusals were removed from REQ-001.008.

R43. Unclaimed-record finding can be noisy
    Severity: medium
    REQ-001.008 reports every file that carries managed metadata but belongs to no
    configured type. Removing a document type on purpose therefore produces findings
    for its former records until they are moved or deleted. This is the intended
    reading of decision 3a-B, but it will surprise a user who removes a type.

R44. Business rules still describe the old configuration model
    Severity: high
    BR-016 (configuration keys and precedence) still describes `enabled`, seed fill
    and collection replace; BR-001/BR-004/BR-009..BR-020 still cite requirement IDs
    that are now archived. The re-pointing pass is still owed.

R45. The init offer is fixed to the Seed
    Severity: low
    REQ-001.006 offers only task, milestone, release, the decision types and the Seed
    entries. A project that wants its own type at init must add it by editing the
    configuration afterwards. This is deliberate but worth stating in user
    documentation.

R46. `id_padding` change no longer states a re-display rule
    Severity: low
    REQ-001.005 says existing identifiers are never re-padded and the wider number is
    used, but does not say whether a changed `id_padding` changes how existing
    identifiers are displayed. Current reading: identifiers are stored values and
    changing `id_padding` affects only newly allocated numbers.

.001 Manage Tasks, .002 View and List Backlog Items, .005 Manage Milestones,

Words: REQ-002 + REQ-003 were 2,169; the merged group is 2,976 (+37%), because the

R52. Releases gain archive and delete (new capability)
    Severity: high (product change)
    No `release archive` or `release delete` exists today, and the lifecycle was
    `planned -> released` with "releases are never archived". REQ-002.004 defines
    `planned -> released -> archived`, an archive folder `backlog/archive/releases/`,
    and a delete with confirmation. REQ-007.001 was updated accordingly.
    Consequences: CLI verbs, ADR/BR-007 ("document archive semantics never apply to a
    release") and the board (archived releases hidden) must follow.

R53. Milestones gain acceptance criteria (new capability)
    Severity: high (product change)
    `papyrus milestone create|edit` accept no `--ac` today. REQ-002.005 now defines
    repeatable acceptance criteria stored as bullets in the milestone body. BR-006,
    the milestone browser view (UI-002) and any templates must follow.

R54. `--ac` view option is new for tasks and milestones
    Severity: medium
    `papyrus task view --ac` and `papyrus milestone view --ac` are required by
    REQ-002.002 but exist for neither verb.

R55. Identifier gap in the REQ-002 numbering
    Severity: low
    The new atomics are .005 and .006, not .003 and .004, because archived records
    keep their numbers (identifiers are never reused). The group now reads
    .001, .002, .005, .006; the gap is intentional and should not be filled.

R56. Business rules contradict the new release and milestone behaviour
    Severity: high
    BR-006 and BR-007 cite archived REQ-003.001/.002; BR-007 states that archive
    semantics never apply to a release, which REQ-002.004 now contradicts. BR-006
    predates milestone acceptance criteria.

R57. UI specifications still describe the pre-merge model
    Severity: medium
    UI-002 cites the archived Backlog atomics and the old milestone shape (no
    acceptance criteria, no release archive). It must be revised with the merge.

GROUP REQ-004 — Decision Records
(reviewed, changes applied)
====================================================================

State after review: 3 active atomics. 634 -> 1,718 words (+171%) because the review
also added a status-verb model, frozen content, delete, and archiving.
Active: .001 Manage Decisions, .002 Change Decision Status, .003 Inspect Decisions.

R58. Decision status verbs are new
    Severity: high (product change)
    REQ-004.002 requires `decision accept|reject|deprecate|supersede --by|archive`.
    The CLI exposes only `edit --status` and `edit --superseded-by`, which must be
    removed in favour of the verbs.

R59. `decision delete` is new
    Severity: high (product change)
    There is no delete verb today. REQ-004.001 requires one, allowed only while the
    status is `proposed`.

R60. Content freeze outside `proposed` is new
    Severity: high (product change)
    `decision edit` currently edits any decision. REQ-004.001 requires editing and
    deleting only while `proposed`, and every other state to reject with no write.

R61. "archived" now means two different things
    Severity: medium
    For decisions it is a status value that moves no file; for documents it is a
    storage location. REQ-007.001 and REQ-004.002 state the distinction, but the CLI
    help, business rules, and UI must not conflate them.

R62. BR-008 contradicts the new decision model
    Severity: high
    BR-008 states that `decision archive` is dropped and that decisions use exactly
    five statuses. Both are now false.

R63. Supersession status mismatch
    Severity: high (correctness)
    The implementation stores the `## Status` value "Superseded by ADR-XXX" while the
    requirements say the value is `superseded` and the successor lives in the
    front-matter `superseded_by` key. The implementation must change, or every existing
    decision file carries a value outside the vocabulary.

R64. Archived decisions stay viewable — assumption to confirm
    Severity: medium
    REQ-004.003 states that an archived decision remains viewable by identifier (it
    stays in place and is historical). Documents behave differently: an archived
    document is unreachable. If decisions should instead be unreachable, that
    requirement clause must be inverted.

GROUP REQ-008 — User Documentation  (new)
====================================================================

Group created with 3 atomics: .001 Provide the Papyrus Manual, .002 Provide
Per-Command Help, .003 Provide the Help Command. REQ-001.004 hands its help clause to
this group; REQ-007.003 cites .002 for generated document-command help.

R65. `papyrus req create-group` writes a defective group record
    Severity: high (tool defect)
    With `--title`, `--story`, and `--description`, `req create-group` wrote a file
    whose front matter contained only `status: active`: no `id`, `title`,
    `created_date`, or `updated_date`. The requirement was invisible to `req list`
    and absent from the browser. It was repaired by writing the front matter through
    `papyrus req edit REQ-008 --editor`. A regression test is needed for group
    creation through the option form (the positional form is untested as well).

R66. NFR-003.003 contradicts dynamic document commands
    Severity: medium
    It requires "a man page for every command", but document-type commands are
    generated from configuration and cannot be enumerated statically. REQ-008.001
    documents the family once and defers per-type options to `--help`. The NFR must
    say "every built-in command". Not edited in this pass.

R67. `papyrus help` currently prints CLI usage, not the manual
    Severity: medium (product change)
    REQ-008.003 requires `papyrus help` to print the manual and `papyrus help
    <COMMAND>` to print that command's help. Neither exists today.

R68. The manual source lives in the README
    Severity: medium
    `papyrus(1)` and `papyrus-config(5)` are sections of README.md today. REQ-008.001
    requires one packaged source from which the installed pages and `papyrus help`
    are generated. Moving the source out of the README while keeping the README
    readable is a documentation restructuring, not a requirements task.

R69. Timestamps corrected after the fact
    Severity: low
    Ten records created during this session carried hand-written `updated_date` (and
    in five cases `created_date`) values later than the actual creation time. They
    were reset to the file modification time through the CLI editor. Future writes
    should rely on the writer's automatic timestamps.

# REQ-005.007 Archive and Delete Document Records

## User Story
As a project maintainer, I want to archive or delete a document record so that inactive documentation leaves the working set while its identity survives until I deliberately delete it.

## Group

REQ-005 Project Documentation Management

## Criticality

Must have

## Description
Every document type declared in the project configuration has the main status `active` or `archived`, and those two values are the only statuses that affect storage location. A record starts at its type's `default_status` when one is configured, otherwise `active` (REQ-007.002). A type may declare further custom statuses (REQ-007.001): they are front-matter values only, cause no file move, and create no folder of their own.

The rules of this requirement are identical for all three document models and do not depend on a type's field sequence or role field sets.

**Archive.** `papyrus <slug> archive <ID>` sets the record's status to `archived` and moves its file into the `archived/` subfolder of the type's configured directory. Archiving preserves the record identifier (REQ-001.005). A custom status is replaced by `archived` and the previous value is not retained. Archived records are hidden from lists, search, and the browser, and the browser shows the shared not-found page for them (REQ-005.017). For a `SingleHtmlMockup` record, the state moves to `archived` in its HTML metadata and the file moves the same way (REQ-005.008).

**No restore.** No command returns an archived record to `active`. This is a product decision, not a missing capability. Only the `archived/` subfolder is recognised as archive storage.

**Misplaced records.** When a record's stored status is `archived` while its file still resides in the type's active folder — a hand-edited file or an interrupted write — any read, list, view, search, or browser path relocates the file to the `archived/` subfolder before returning it, using the same write-then-remove sequence as `archive`, and reports the relocation in diagnostics. If the relocation fails, the record is returned read-only with a validation outcome and writes to it are refused until the conflict is resolved.

**Delete.** `papyrus <slug> delete <ID>` permanently removes a record. A record that is not archived is archived first and then removed. Deletion asks for confirmation, and `--force` skips the prompt. A deleted record leaves no file, and its identifier is not reused: allocation is the highest observed number plus one across active and archived locations, with no high-water mark, so deleted numbers generally remain gaps and deleting the highest record makes its number available again.

**GroupedMarkdown.** Archive and delete apply per record. Archiving or deleting a group record changes none of its members, and each member keeps its file, status, and identifier (REQ-005.001).

## Acceptance Criteria

- Every configured document type has the main status `active` or `archived`, and may declare custom statuses that never affect storage location.
- A new record starts at its type's `default_status` when one is configured, otherwise `active`.
- A custom status causes no file move and creates no per-status folder.
- `archive <ID>` sets the status to `archived` and moves the file to the `archived/` subfolder of the type's directory.
- Archiving a record that carries a custom status sets the status to `archived` and does not retain the previous value.
- Archiving preserves the record identifier.
- Archived records are hidden from lists, search, and the browser, and the browser shows the shared not-found page for them.
- A `SingleHtmlMockup` record moves to the `archived` state in its HTML metadata and its file moves in the same way.
- No command returns an archived record to `active`; no restore command exists.
- Only the `archived/` subfolder is recognised as archive storage; a `deprecated/` subfolder is not read, migrated, or inventoried by any command, including `papyrus check`.
- When a record's stored status is `archived` while its file is in the active folder, any read, list, view, search, or browser path relocates it to `archived/` before returning it and reports the relocation in diagnostics.
- When that relocation fails, the record is returned read-only with a validation outcome and writes to it are refused until the conflict is resolved.
- `delete <ID>` permanently removes the record, archiving it first when it is not archived.
- Deletion requires confirmation, and `--force` skips the prompt.
- A deleted identifier is not reused: allocation is the highest observed number plus one across active and archived locations, with no high-water mark.
- Archiving or deleting a group record of a `GroupedMarkdown` type leaves every member's file, status, and identifier unchanged.
- The rules apply to every configured document type and do not depend on a type's document model, field sequence, or role field sets.

## Open Questions

- None. Deleted-identifier allocation, relocation on read, and the inert `deprecated/` folder are settled as stated.

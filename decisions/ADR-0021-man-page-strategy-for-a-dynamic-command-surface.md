# Man Page Strategy for a Dynamic Command Surface

## Status
proposed
## Date

2026-11-13

## Context

NFR-03.003 requires Papyrus to "provide a man page for every command", to include those man pages in the Debian package, to keep **Markdown sources under `docs/man/`**, to generate roff at build time, and to install the result to the standard man paths in the `.deb`.

REQ-07.002/REQ-07.003 change what "every command" means. The command set is now `built-ins + one command per enabled `document_types` entry`, and the entry set is per project and editable at runtime: a project may rename `req`, disable `glossary`, or add a command that exists in no other project.

Observed state:

- `docs/man/` does not exist. The only man-page-shaped content is rendered inside `README.md` as `<pre>` blocks: a `papyrus(1)` section (line 19) and a `papyrus-config(5)` section (line 1327). There is no roff source and no generator.
- `scripts/build-deb.sh` stages only `/usr/bin/papyrus` and `/usr/share/doc/papyrus/copyright`; nothing is installed under `/usr/share/man`. `packaging/deb/` mirrors that layout.
- ADR-0002/ADR-0003 restrict the package to Debian Forky amd64 and ADR-0005 keeps the binary dependency-free; ADR-0001 allows Node.js/Python 3 as **build-time** tooling only.
- ADR-0016 replaces the static clap enum with a tree built from the artifact registry, so built-in help text is generated at runtime from `cli::BUILTIN_COMMANDS`; document-type help is generated per project.
- The packages are installed machine-wide (`/usr/share/man`), while the command set is project-local. A man page for a command that does not exist in the reader's project is wrong; a man page missing for a command that does exist is also wrong.

The impossibility is precise: **a packaged static man page cannot describe a runtime, project-specific command name.** Something in NFR-03.003's scope has to be defined: either "every command" means every built-in command plus the document command family (with per-slug documentation produced per project), or the package must ship a page per default slug and accept that pages for renamed/disabled slugs exist and that user-added slugs have none.

REQ-07.003 now records the consequence explicitly: NFR-03.003 covers built-in commands, config-defined slugs have no man page in this release, and that gap is carried as a release risk without amending the NFR. NFR-03.003 itself is unchanged and still asks for "a man page for every command".

Forces: NFR-03.003 is a validated requirement and may only be amended by `requirements-engineer`; packaging must stay reproducible and offline; no new runtime dependency; man pages are also development input and must not silently drift from the CLI; the release cannot claim NFR-03.003 compliance as written while document slugs have no page; and the owner has deferred the choice, so no implementation may assume one.

## Decision

1. **No option is selected.** The project owner deferred this decision on 2026-11-13. Nothing in this ADR authorises a man-page implementation, a new command, or a packaging change, and no agent may treat any candidate below as chosen. The ADR records the constraints, the candidate options, and their consequences so the decision can be taken later without re-analysis.

2. **What is decided regardless of the option.**
   - The gap is real and must be carried as a release risk: a machine-wide package cannot contain a page for a project-defined command name, so NFR-03.003's literal reading and REQ-07.002/REQ-07.003 cannot both hold for user-added slugs.
   - Any chosen option must keep man-page sources as Markdown under `docs/man/` and generate roff at build time, because that construction is what NFR-03.003 mandates independently of scope.
   - No option may add a runtime dependency, a runtime asset directory, or a network fetch (ADR-0005). Build-time tooling remains limited to what ADR-0001/ADR-0002 permit.
   - Man pages must not be generated by re-rendering clap help: clap's about lines carry no semantics, exit codes, or examples, so a generated page would be a stub and would still need hand maintenance.
   - `README.md` cannot remain a second maintained copy of `papyrus(1)`/`papyrus-config(5)`; whichever option is chosen, the packaged pages are the reference and the README points to them.

3. **Mechanics required by any option that ships Markdown sources** (common groundwork, not a selection):
   - sources `docs/man/papyrus.1.md`, `docs/man/papyrus-config.5.md`, and — if a family page is chosen — `docs/man/papyrus-document.1.md`;
   - an in-repo, stdlib-only `scripts/md2man.py` (Python 3, build-time only) supporting `NAME`, `SYNOPSIS`, `DESCRIPTION`, `COMMANDS`, `OPTIONS`, `EXIT STATUS`, `FILES`, `ENVIRONMENT`, `EXAMPLES`, `SEE ALSO` and emitting `TH`/`SH`/`SS`/`TP`/`PP`/`IP`/`.B`/`.I`;
   - output under `target/man/man1` and `target/man/man5`, gzipped with `gzip -9n`;
   - `scripts/build-deb.sh` staging `usr/share/man/man1/*.1.gz` and `usr/share/man/man5/*.5.gz`, with `packaging/deb/` mirroring the tree;
   - a build-time `groff -man -Tutf8` (or `man --warnings`) pass that fails on warnings, and a packaging test that unpacks the `.deb` and asserts each committed page is installed.

4. **Candidate options (none selected).**

   | # | Option | What ships | Consequence |
   |---|---|---|---|
   | A | Three pages: `papyrus(1)`, `papyrus-config(5)`, `papyrus-document(1)` describing the baseline verbs, `status`, archive/delete, the generic content model, and the eleven default slugs | Full coverage of every command that exists in every project; no page for a user-added slug | Smallest maintenance surface; `man papyrus-<custom>` does not exist; NFR-03.003's literal reading is not met for configured slugs |
   | B | A + one stub page per default slug (`papyrus-req(1)` … `papyrus-test-report(1)`) generated at build time from the static default table | Literal coverage of the default set | Pages for renamed or disabled slugs describe commands absent from that project; user-added slugs still uncovered; more pages to keep in sync |
   | C | A + `papyrus help --man`, which renders a roff page for the **effective** project command set (built-ins plus enabled slugs) to stdout, with optional `--output` inside the project only | Every command a given project actually has is documentable on demand, generated from the registry so it cannot drift | A second, runtime rendering path; the generated page is not in the package and must be produced per project; adds a `help --man` surface (no new top-level command) |
   | D | Built-ins only; no document-family page and no per-slug mechanism | Minimal | Leaves the document command family undocumented in the package and does not address NFR-03.003 for those commands at all |

   Options A and C can be combined; B and C can be combined; D is the fallback that concedes the gap for the whole family. The earlier draft's recommendation (A + C) is retained only as a recorded recommendation for the future decision, not as a decision.

5. **What the future acceptance must state.** The accepting ADR or amendment must say (a) whether NFR-03.003 is narrowed to built-ins plus the document family, or left literal with per-slug pages, (b) whether per-project generation is provided, and (c) which `text/roff` verification gates the release. Until then, no man-page work may start, and the release notes must not claim NFR-03.003 compliance for configured slugs.

## Consequences

**Positive (of any option that follows decision 3's groundwork):**

- Man pages stop being a copy of the README and become maintainable Markdown with a build step, an install path, and a build-time verification — which is what NFR-03.003 asks for independently of the scope question.
- A packaged page cannot describe a command the binary lacks, because the page describes built-ins (static) and the document *family* (not individual slugs).
- No new runtime dependency, and the build keeps working offline on Forky.

**Negative (of deferring):**

- NFR-03.003 remains unsatisfied as written for configured document slugs, and the release must carry that as a known risk rather than a completed requirement.
- `docs/man/` stays empty and `scripts/build-deb.sh` keeps shipping no man pages, so the packaging gap grows the longer the decision is deferred.
- Every further change to the command surface (a new baseline verb, a new extension verb) leaves the future man pages further behind; the inventory test of decision 3 cannot run until the sources exist.

**Negative (specific to the candidate options):**

- Option A: `man papyrus-<custom>` does not exist, so a user-added slug is documented only in `papyrus-document(1)`.
- Option B: pages exist for slugs a project may have renamed or disabled, and user-added slugs remain uncovered.
- Option C: a second, runtime rendering path to maintain, and the generated page is not in the package.
- Option D: the whole document family is undocumented in the package.
- All options: build complexity grows by one script, one directory, and one verification step, and `groff` becomes a required build-time tool.

**Risks and mitigations (pending the decision):**

- *Scope decided implicitly by implementation*: no man-page work may start before the option is accepted; this ADR is the record that the choice is open.
- *Drift between `BUILTIN_COMMANDS` and the man page*: the inventory test fails the build once the sources exist; until then the risk is that the first implementation hard-codes a stale command list.
- *Generated page unreadable*: the converter must handle a fixed subset, and every page is rendered during packaging with `groff` warnings failing the build.
- *README removal loses content*: the Markdown sources must be derived from the README sections before removal, and the README keeps a pointer.
- *Release compliance claimed too early*: the release notes must state that NFR-03.003 is not met for configured slugs, matching REQ-07.003's recorded risk.

## Alternatives Considered

The candidates are listed in decision 4 and none is selected. The options rejected on their merits, independently of the deferred scope question, are:

| Option | Outcome | Reason |
|---|---|---|
| Generate man pages at runtime into `docs/man/` automatically on first use | Rejected | Writes on read paths, mutates the project without a command, and duplicates content that belongs to the package. |
| Generate `papyrus(1)` from clap's help at build time | Rejected | Clap help has no prose for semantics, exit codes, or examples; the page would be a stub and still need hand maintenance. |
| Document document commands only in `--help`, with no man pages | Rejected by NFR-03.003 | The requirement explicitly forbids deferring the man page. |
| `pandoc` or `go-md2man` as the converter | Rejected | Adds an unverified build dependency on Forky; a standard-library converter is smaller and auditable. |
| Leave the decision to the implementation task | Rejected | The scope question changes what NFR-03.003 means, so it is an owner decision, not an implementation detail. |

## Open Questions

- **Owner decision required (deferred 2026-11-13)**: option A, B, C, D, or a combination — and, with it, whether NFR-03.003 is narrowed or kept literal.
- Should `papyrus help --man`, if chosen, be named `papyrus man`? An unselected option; `help --man` would avoid adding a reserved name.
- Should the README keep a rendered copy of `papyrus(1)` for browsing on the web? Current lean: no, pointer only.
- Should the inventory test compare against `cli::BUILTIN_COMMANDS` at build time (a generator) or at test time (a check)? Deferred with the option.

## Downstream constraints

1. No man-page implementation may start until the owner accepts an option; this ADR does not authorise one.
2. If an option shipping Markdown sources is accepted, `docs/man/` becomes the only man-page source and no other file may be converted into a packaged page.
3. If accepted, `scripts/build-deb.sh` must install the pages and a packaging test must assert them; a package without them fails NFR-03.003 verification.
4. Any chosen option must keep the build offline and dependency-free at runtime.
5. Until the decision is recorded, releases must not claim NFR-03.003 compliance for config-defined document slugs, and the release notes must say so.

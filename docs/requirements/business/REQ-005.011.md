# REQ-005.011 Maintain Record Metadata Through Commands

## User Story

As a project contributor, I want commands to set and maintain record metadata automatically so that metadata stays accurate without manual editing.

## Group

REQ-005 Project Documentation Management

## Criticality

Must have

## Description

**Automatic values.** `created_date` is set when a record is created and never changes afterwards. `updated_date` is set at creation and refreshed by every write, including a browser save; for a decision record it is refreshed only when the status changes (REQ-004.001). `id` is generated and stable (REQ-001.005). These three values have no command option.

**Status exemption.** For a document record, `status` has no create or edit option either: a new record starts at its type's `default_status`, or at `active` when none is configured, and the value changes only through the `status` and `archive` verbs (REQ-007.001). The status of a task, milestone, release, or decision keeps the behaviour of its own category (REQ-002, REQ-003, REQ-004).

**Options come from the field sequence.** For a document record, the remaining options are the declared fields of the type's field sequence for the record's role: each field contributes one option on the verbs listed in the field, named by its `option` or by its `key` in kebab case when no option is declared (REQ-007.003). A field whose verbs exclude `edit` has no edit option and is never writable after creation, and a field whose verbs exclude `create` has no create option. The field sequence is the option and help order. `title` is not a field: it is the first positional `TITLE` on `create` and `create-group`, is accepted as `--title` on `create`, `create-group`, and `edit`, and can never be cleared by an edit. The engine-owned `group` link of a member record never has an option. `--label` and `--reference` remain the general repeatable metadata options (REQ-005.010).

**One write path.** A create and an edit each produce one patch of operations — set a front-matter key, set or clear a body section, set the heading title, and the model-specific group-link, HTML-metadata, and supersession changes — and a single writer applies the patch atomically. A patch that changes nothing performs no write, and a validation failure writes nothing. The browser submits its edits through the same path.

**What a write preserves.** Every command that writes a record preserves the front-matter keys and body content the operation does not change, including an undeclared front-matter key already on disk, which is never repaired, merged, or removed. This covers create, edit, status, archive, delete, supersede, milestone close, and release close.

**Adoption.** An existing managed Markdown record that does not yet carry a front-matter block gains one on its first read and on its first write; no bulk migration command is required, and adoption is idempotent. Adoption covers only files claimed by a configured document type or by another managed record category; prose Markdown and HTML records are excluded. Adoption changes nothing in the body, except that a value still held in a legacy body section moves to front matter when its record is written, so no value is stored twice.

**Backlog records.** `ordinal` belongs to backlog records only: it is an opaque non-negative integer supplied through a create or update option and defaulted from the current maximum. No document type declares an `ordinal` field.

## Acceptance Criteria

- `created_date` and `updated_date` are set when a record is created, and `created_date` never changes afterwards.
- `updated_date` is refreshed by every write, including a browser save, except on a decision record, where only a status change refreshes it.
- `id`, `created_date`, and `updated_date` have no command option.
- For a document record, `status` has no create or edit option; a new record starts at its type's `default_status`, or at `active` when none is configured and changes only through the `status` and `archive` verbs.
- The status of a task, milestone, release, or decision keeps the behaviour of its own category.
- Each declared field contributes one option on the verbs the field declares, named by its `option` or by its `key` in kebab case.
- A field whose verbs exclude `edit` has no edit option, and a field whose verbs exclude `create` has no create option.
- Options and help follow field-sequence order, including the role-appropriate sequence of a `GroupedMarkdown` type.
- `title` is not a field: it is the first positional `TITLE` on `create` and `create-group`, `--title` is accepted on `create`, `create-group`, and `edit`, and an edit cannot clear it.
- The `group` link of a member record has no option and is never writable through create or edit.
- `--label` and `--reference` remain general repeatable metadata options and are not fields.
- A create and an edit each produce one patch that a single writer applies atomically; a patch that changes nothing performs no write, and a validation failure writes nothing.
- The browser submits its edits through the same write path.
- Every write preserves the front-matter keys and body content the operation does not change.
- A write preserves an undeclared front-matter key already on disk and never repairs, merges, or removes it.
- An existing managed Markdown record without a front-matter block gains one on its first read and on its first write, and adoption is idempotent.
- Adoption covers only files claimed by a configured document type or another managed record category, and excludes prose Markdown and HTML records.
- Adoption changes nothing in the record body, and a value still held in a legacy body section moves to front matter on write so that no value is stored twice.
- `ordinal` belongs to backlog records only and is defaulted from the current maximum; no document type declares an `ordinal` field.

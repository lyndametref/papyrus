# REQ-006.014 Display Config-Defined Document Types in the Browser

## User Story

As a project contributor, I want the browser to serve any document type declared in the configuration so that a type added for the command line is also usable in the local web interface.

## Group

REQ-006 Search and Local Web Interface

## Criticality

Should have

## Description

**One surface for every type.** Each document type declared in the configuration is served by one document surface covering its list, single-record view, edit form, submission, conflict, and not-found pages. The surface varies only with the type's document model and descriptor: there is no per-type handler, no per-type page, and no per-type string. A type added by configuration becomes available without a code change. Backlog and decision records keep their own surfaces.

**List.** The list uses the shared list layout of REQ-006.016, the type's declared slots, and the row content of REQ-005.017. It offers a status filter whose options are `active` plus the type's declared custom workflow statuses in configured order; `archived` is never offered because archived records are not listed, and a value outside the offered set is rejected rather than applied. A type that declares no custom status shows only `active`.

**View.** The single-record view renders the record content of REQ-005.017: one section per declared field in sequence order, headed by the field label. A `GroupedMarkdown` group record also shows its members as a read-only list in identifier order, and a member record shows a read-only link to its group; membership is never a form control. A `SingleHtmlMockup` record shows its fixed metadata block instead of field sections (REQ-005.008). Undeclared metadata already on disk is shown read-only after the field sections.

**Edit.** The form follows REQ-006.004. A submission with a stale record version renders the same form with the submitted values and a conflict notice and writes nothing. An identifier that does not resolve — unknown, archived, or of a type that is not configured — returns one shared not-found page.

**Presentation facts.** Every presentation fact comes from the type's configuration entry: label, plural, order, summary, type alias, API aliases, slots, reference visibility, and each field's label, help, sequence position, required flag, kind, and verbs. A field's storage heading is never shown as a display heading; the visible heading is the field label. The browser holds no per-type string or list for a document type.

The document surface is built from one validated configuration snapshot (ADR-037) and requires no network access.

## Acceptance Criteria

- Every document type declared in the configuration has a browser list view and a single-record view.
- A type added by configuration becomes available in the browser without a code change.
- All document types are served by one document surface for list, view, edit, submission, conflict, and not-found pages, with no per-type handler or per-type string.
- The list uses the shared layout of REQ-006.016, the type's declared slots, and the row content of REQ-005.017.
- The list offers a status filter with `active` plus the type's declared custom workflow statuses in configured order, never `archived`.
- A status filter value outside the offered set is rejected rather than applied.
- The view renders one section per declared field in sequence order, headed by the field label.
- A `GroupedMarkdown` group record shows a read-only member list in identifier order, and a member record shows a read-only link to its group; membership is never a form control.
- A `SingleHtmlMockup` record shows its fixed metadata block instead of field sections.
- Undeclared metadata already on disk is shown read-only after the field sections.
- The edit form follows REQ-006.004.
- A submission with a stale record version renders the form with the submitted values and a conflict notice and writes nothing.
- An identifier that is unknown, archived, or of a type that is not configured returns one shared not-found page.
- Every presentation fact comes from the type's configuration entry, and the browser holds no per-type string or list.
- A field's storage heading is never shown as a display heading; the visible heading is the field label.
- The document surface is built from one validated configuration snapshot and requires no network access.

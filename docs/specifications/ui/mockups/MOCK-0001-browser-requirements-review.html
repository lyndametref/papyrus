TASK-6 · m-1

Papyrus local browser: requirement content

One wireframe package for listing, viewing and editing business-requirement and non-functional-requirement records from a project-local, offline browser interface.

Scope

  • Requirement list for the two independent document categories.
  • Record view for requirements and groups, including an unresolved group reference.
  • Edit form for the documented content fields, with dirty, 422 and 409 states.
  • One error layout for every HTML error status.
  • 320 CSS-px behaviour and accessibility annotations.

Package contents

  • Landing — ticket, milestone, sources, approval status, one button per review content.
  • This deck — 12 slides: 9 view slides, decisions, open questions.
  • Web prototype — 25 clickable views with a full view navigation band.
  • Status — approved; explicitly approved by the user on 2026-11-03 (UTC).
  • Convention — grayscale, layout only, no technology choices.

View 1 of 9 · shell

#web/list-business

One shell, one persistent left sidebar

Every page shares the same frame: a header with product, project and the offline note; a left navigation labelled “Document types”; the page body; a footer.

What it shows

  • Header: “Papyrus”, the project name, and a right-aligned “Local browser / offline · 127.0.0.1:6420” note.
  • Persistent left nav “Document types” with vertical choices: Business requirements, Non-functional requirements.
  • The current type is bold, underlined and marked aria-current="page".
  • Main panel with exactly one h1; footer stating that every page is served from this project with no network access.
  • The same shell, including the type navigation, is drawn on list, record, edit and error pages.

Why this way

  • Sidebar, not a top filter. Document type is a stable axis of the record space, not a transient query, so it stays visible on every page and at every depth.
  • It scales by addition. A new record type is one more row; a horizontal filter would compete with the page title and the breadcrumb.
  • Three cues — bold, underline, aria-current — so colour is never the only signal.
  • No top navigation menu. The list is the only top-level page; a second navigation layer would add targets without destinations.
  • Rejected: a top segmented control. It reads as a temporary query, pushes the title down, and does not survive the move from list to record view.

View 2 of 9 · categories

#web/list-business · #web/list-nonfunctional

Two independent categories, one at a time

The sidebar selects the category: business requirements by default, non-functional requirements on request. Only the selected section renders; the other category is absent, not empty.

What it shows

  • Section heading with the group and requirement counts right-aligned.
  • Each group is one bordered row: group ID and title as one link, member count, then the member requirements as a nested list of ID + title links.
  • A trailing “Other requirements” subsection for requirements whose stored group reference does not resolve.
  • Switching category keeps the page structure and changes only which section is rendered.
  • Active elements: 2 sidebar links, 1 group link per group, 1 link per member, 1 link per “Other” row.

Why this way

  • Separate categories, not a filter. Business and non-functional records have their own directories, prefixes and group numbering; one merged list would imply a shared namespace.
  • One section per page removes a scroll region and the “which section am I in” question.
  • Counts on the header line so volume is known before scanning and the title keeps its line.
  • Members inside their group so a requirement is one click away and the two-level structure is visible without opening the group.
  • Rejected: a single page listing both categories (the earlier design). It duplicated headings, doubled the scroll and made the sidebar look like a filter.

View 3 of 9 · list states

#web/list-empty-project · #web/list-empty-type · #web/list-group-empty · #web/list-long

Empty and edge states keep their frame

Four states of the same page: no records at all, the selected category empty while the other has records, a group with no members, and many groups with long or unbreakable titles.

What it shows

  • Empty project: the selected section keeps its heading and the count reads “No groups”; a dashed box states that no records were found and that records are created from the command line.
  • Empty category: only the selected section renders, with its empty state and a pointer to the other category in the sidebar.
  • Group with no members: the row is kept, the count reads “No requirements”, and an in-row note says so.
  • Long content: group titles wrap; an unbreakable requirement title wraps inside the row; no ellipsis and no horizontal scrolling.

Why this way

  • Dashed boxes read as absence, not as a disabled control, and the sentence names both cause and remedy.
  • The header keeps its shape with “No groups” and zero counts, so the page does not collapse into a bare message.
  • An empty category keeps its frame so the user learns the structure exists and only the content is missing.
  • A group with no members stays reachable; removing it would hide a record that exists.
  • Wrapping, never truncation: the identifying part of a title is usually at the end.
  • Rejected: a centred empty-state hero with an illustration. It hides the page structure and implies a create action this increment does not offer.

View 4 of 9 · record view

#web/view-req-business · #web/view-req-nfr

Record view: identifier, title, one action

A business requirement with a user story and a non-functional requirement without one: breadcrumb, ID in monospace above the title, one right-aligned Edit action, read-only metadata, then the story and description blocks.

What it shows

  • Breadcrumb: Requirements › owning group (when resolvable) › record ID (current, not a link).
  • Record ID in small monospace text, then the record title as the only h1.
  • Primary “Edit” button, right-aligned on the title line; no second action.
  • Read-only metadata as a definition list: Record ID, Record form, Document type, Owning group.
  • “User story” section only for business records that have one; “Description” with line breaks preserved and references left literal.

Why this way

  • One primary action. Editing is the only write in this increment, so Edit is the only filled control and it sits on the title line.
  • “Back to requirements” removed. The breadcrumb already goes up; two ways back would compete with the one action.
  • Metadata as a definition list, not disabled inputs. Those values are facts, are never submitted, and must not look editable or take focus.
  • The story block is omitted for non-functional records instead of shown empty, so the page has no dead region.
  • Rejected: a toolbar with Edit, Back, Delete and Deprecate. It would advertise operations this increment does not implement.

View 5 of 9 · group pages

#web/view-group-business · #web/view-group-nfr · #web/view-unresolved

Group pages list what the group contains

A group page must answer “what is in here?”. After its own fields it lists the member requirements; an unresolved group reference on a requirement page stays plain text.

What it shows

  • Business group with a story and “None (group record)” as owning group.
  • Non-functional group without a story.
  • “Requirements in this group” section: ID + title links in ascending ID order.
  • Unresolved ## Group reference shown as stored text with “(not an active group)”, not a link, and absent from the breadcrumb.
  • Active elements: breadcrumb, owning-group link, Edit, member links.

Why this way

  • Member list on the group page turns the group into a hub; linking back to a filtered list would lose the group context the user came for.
  • The member rows reuse the list’s ID + title link shape, so both screens read the same way and link text stays descriptive out of context.
  • Unresolved references are plain text with a note: linking to a 404 would be a trap.
  • “None (group record)” states absence explicitly; a blank field would read as missing data.
  • Rejected: a “group contents” table with columns. At this size the list is shorter, wraps better, and matches the requirement list.

View 6 of 9 · edit form

#web/edit-business · #web/edit-nonfunctional

Edit form: known facts above, editable fields below

Pristine business form with title, user story and description; pristine non-functional form with title and description only. Read-only metadata first, help text under each label, Save and Cancel last.

What it shows

  • Breadcrumb Requirements › record ID › Edit (current).
  • h1 “Edit <ID>” and the current title as a muted line.
  • Read-only metadata block; its owning group is a link, the other values are never inputs.
  • Title text input marked required, with help “1 to 200 characters · shown in lists and headings”.
  • User story textarea on business forms only; description textarea on all forms.
  • Hidden version token drawn as a dashed annotation; primary “Save changes” and outlined “Cancel” link.

Why this way

  • Metadata first so the user confirms what is being edited before typing; its flat, unboxed treatment separates it from the inputs.
  • Labels above fields with the rule beneath, so the constraint is read before the mistake, not after it.
  • The story field exists only on business forms; the non-functional form is shorter rather than showing a disabled control.
  • Save is filled, Cancel is an outlined link: one primary action, one exit that never writes.
  • Rejected: placeholder-only labels. They vanish as soon as the user types and leave the field unlabelled.

View 7 of 9 · recovery

#web/edit-dirty · #web/edit-errors · #web/edit-conflict · #web/view-after-save

Recovery states: dirty, 422, 409

Unsaved changes; a validation failure with a summary, linked errors and every typed value kept; a conflict where nothing was written and the attempted values are shown read-only.

What it shows

  • Dirty: an “Unsaved changes” status beside the heading; Save stays enabled; the leave guard is script-only.
  • 422: summary box with role="alert", “There is a problem”, one link per error, “Nothing was saved. Your typed values are kept below.”
  • Field errors directly below the field, prefixed “!”, with aria-invalid="true" and a thicker border.
  • 409: its own page — “This record changed on disk”, the contract message, primary “Reload the form”, then the read-only copy of the attempted values.
  • After save: the ordinary record view re-read from disk, with no success banner.

Why this way

  • The summary sits at the top of the form, under the metadata and above the first field: it is the first thing after the heading and its links jump to each field.
  • Nothing typed is discarded, so recovery is fix-and-resubmit, and the summary says so.
  • Dirty is a status line, not a disabled Save. Disabling Save would need script and break the no-JavaScript requirement.
  • Conflict is its own page with one primary recovery; the read-only copy comes last so it can be copied first.
  • Rejected: a transient toast for errors. It is not focusable, disappears, and cannot link to the field at fault.

View 8 of 9 · errors

#web/error-404-unknown · … · #web/error-500

One error layout, six messages

A large monospace status code, a plain-language heading, one explanatory sentence, a muted hint and a single “Back to requirements” link. Variants: 404 unknown, 404 deprecated, 400, 405, 415, 500.

What it shows

  • The status code is the largest element; the readable message follows as the h1.
  • One sentence of explanation and one muted recovery hint.
  • Exactly one link: “Back to requirements”.
  • The shell stays (header, type navigation, footer) so the page still looks like Papyrus.
  • Six screens in the prototype, one per status.

Why this way

  • The taxonomy lives in the words, not the layout: users learn one recovery pattern and apply it to every failure.
  • The status code is largest because it is what a user reports or searches for.
  • Exactly one way out. No retry button, no imitation of browser history, no action that cannot succeed.
  • No paths, request bodies or internal detail; the two 404 variants stay deliberately non-revealing about deprecation.
  • Rejected: a distinct layout or illustration per status. It forces the user to relearn recovery on every failure.

View 9 of 9 · narrow and assistive technology

#web/responsive-list-320 · #web/responsive-edit-320

320 px and accessibility, drawn beside a legend

The list and the edit form at 320 CSS px, each next to a numbered annotation legend: stacked header, collapsed type toggle, stacked group rows, full-width fields, stacked Save and Cancel.

What it shows

  • A 1:1 320-px frame beside a numbered legend, on the same 1440-px review canvas.
  • Header stacks; the “Local browser” note is omitted at this width.
  • The document-type sidebar collapses to one labelled toggle with aria-expanded and aria-controls; the links still work without script.
  • Group rows stack: ID, wrapping title, member count on its own line, then member links.
  • Edit fields are full width; Save and Cancel stack and span the column.
  • Numbered annotations: landmarks, heading order, sidebar semantics, link text, focus ring, labels, metadata as a definition list, error wiring, contrast, no-JavaScript, hidden version token.

Why this way

  • 320 px is the narrowest supported width and the place where every stacking decision shows.
  • A 1:1 frame plus a numbered legend keeps the rules auditable without a second document.
  • Long words wrap inside the row and text never scrolls sideways, so 200% zoom behaves the same way.
  • Save and Cancel stack and span the column, keeping a comfortable target instead of shrinking the primary action.
  • Rejected: arrows drawn over the wireframe. They obscure the layout; numbers can be cited one by one.

Cross-cutting decisions

all views

Decisions that apply to every view

These rules hold across the whole prototype; each is visible somewhere in the 25 screens.

Navigation and state

  • Plain links everywhere: sidebar category, group, member, breadcrumb, Edit, Cancel, error recovery. No control depends on script.
  • The list is the only top-level page; record, edit and error pages hang off it and always offer a way back through the breadcrumb or the error link.
  • Empty and error states keep the type navigation visible, so recovery is one click and the user never lands in a dead end.
  • Nothing on any page creates, deprecates, restores, deletes, moves or searches records.

Responsive, accessible, technology-neutral

  • One stacking behaviour for 320 px and 200% zoom; no horizontal scrolling of text.
  • Landmarks header, nav, main, footer; one h1 per page; no skipped heading level.
  • Every control has a visible label; errors are associated and announced; the focus ring is 2 px with 2 px offset.
  • Status and errors are never conveyed by colour alone.
  • No library, framework, component set, icon font or brand colour is implied anywhere.

Open questions and approval

MOCK-0001 · approved

Open items before implementation

These are design decisions or specification gaps found while mocking up. Each needs confirmation or a specification note before the UI is implemented.

Design and specification gaps

  • Unknown sections are preserved but not displayed. Show them read-only? (Recommended: yes — users cannot see what they are preserving.)
  • Success feedback: after a save the record view is shown with no banner. Confirm silence, or add a brief inline “Saved” status.
  • Dirty state: Save stays enabled and the leave guard is script-only. Confirm.
  • 404 wording: unknown and deprecated use distinct but non-revealing messages. Confirm which ships.
  • Project name in the header comes from the project directory; confirm the source.
  • Edit metadata shows the owning group ID only; confirm that is enough at 320 px.
  • Conflict page repeats attempted values read-only; confirm this addition.

Package and approval

  • Single-category model: the specification (§4.6–4.9) still describes a two-section list with type=all; this package follows the revised persistent sidebar with two independent categories and no “all”. The specification wording is updated only after approval.
  • Empty project copy speaks about the project (“no requirement records were found”) while only the selected category renders. Confirm this wording.
  • Counts exclude deprecated members; wording is “2 requirements” / “1 requirement” / “No requirements”.
  • Header note prints the bind address; confirm it is wanted on a non-loopback bind.
  • Status: approved — explicitly approved by the user on 2026-11-03 (UTC).

REQ-06 Search and Local Web Interface

User story

As a project contributor, I want to open a local web interface over project stores so that I can access project information through a browser.

Description

The browser command serves the local web UI over both backlog and documentation stores. Its default bind address is 127.0.0.1 and default port is 6420; the host and port can be selected. A non-loopback host is permitted but causes a warning.

The default browser opens automatically unless disabled by option or configuration.

Requirement references such as REQ-05.001 and NFR-04.002 are shown as literal text, and Markdown punctuation such as ** is not interpreted.

Accessibility annotations — list at 320 CSS px

  1. Landmarks: header, nav (document types or breadcrumb), main, footer. The project name is text, not a link.
  2. One h1 per page; the type section is h2; groups are h3. No heading level is skipped.
  3. The document-type sidebar is one nav labelled “Document types” with vertical links; the current link uses aria-current="page" plus bold and underline. At this width it collapses behind a labelled toggle with aria-expanded and aria-controls; the links still work without script.
  4. A group row is one link (ID + title) with the member count as adjacent text; deprecated members are not counted.
  5. Member links read as ID + title, so they are descriptive out of context.
  6. Focus order follows document order: sidebar links, then each group link, then its member links. The focus ring is 2 px with 2 px offset and stays visible on every control.

Also: at 320 CSS px and at 200% zoom text wraps without horizontal scrolling; body and muted text meet 4.5:1 contrast; empty states and counts are words, not icons or colour; no JavaScript is required because the type links and records are plain links.

Accessibility annotations — edit form at 320 CSS px

  1. Landmarks: header, nav (breadcrumb), main, footer. The breadcrumb is a nav containing a list; its last item is the current page and is not a link.
  2. Heading levels: h1 “Edit REQ-06.002”, then h2 for each section. No level is skipped.
  3. Every control has a visible label associated by for/id. The required field says “required” in the label text and sets the required attribute.
  4. Read-only metadata is a definition list, not disabled inputs, so it is neither focusable nor submitted.
  5. Save is a submit button and stays enabled; with JavaScript unavailable the form still posts. The version token is a hidden input: never visible, never focusable, always submitted.
  6. Cancel is a link back to the record view without saving. Focus order is breadcrumb, read-only link, title, story, description, Save, Cancel; actions stack at 320 px and remain keyboard reachable.

Error annotations: the summary has role="alert" and links to each field; each field message is referenced by aria-describedby and the field has aria-invalid="true". Error text names the field and what to change, never colour alone. Contrast stays at 4.5:1 and the focus ring remains visible. Without JavaScript, validation re-renders on the server with typed values kept, and only the unsaved-changes warning is absent.

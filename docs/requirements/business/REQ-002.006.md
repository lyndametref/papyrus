# REQ-002.006 Manage Releases

## User Story

As a project maintainer, I want to create, close, archive, and delete releases so that milestones can be grouped for planned delivery and finished delivery records leave the working set.

## Group

REQ-002 Backlog Management

## Criticality

Must have

## Description

`papyrus release create <TITLE>` creates a release with a title, an optional description, and general labels and references. Its identifier uses the configured release prefix and the shared `id_padding` (REQ-001.005); with default configuration the first identifier is `REL-001`. A release may contain multiple milestones, while each milestone is assigned to at most one release (REQ-002.005).

**Lifecycle.** The release lifecycle is fixed by the backlog category (REQ-007.001): `planned`, then `released`; archived is a file position. A new release starts `planned`, and the state is stored in the front-matter `status` field (REQ-005.010). The lifecycle is not configurable, and there is no restore command.

`papyrus release close <ID>` changes `planned` to `released`; `released` means the delivery happened. Closing a release that is not planned is rejected with a validation outcome and writes nothing. `papyrus release archive <ID>` moves the file to the backlog archive folder for releases; the status is not modified. An archived release is hidden from active lists and from the Backlog board, keeps its identifier, remains viewable, and is not editable.

**Edit.** `papyrus release edit <ID>` changes the title, the description, the labels, or the references. No option sets the lifecycle state apart from `close` and `archive`.

**Delete.** `papyrus release delete <ID>` permanently removes the release. Deletion asks for confirmation, and `--force` skips the prompt.

**Milestones are not cascaded.** Archiving or deleting a release changes no milestone: each milestone keeps its file, its state, and its release assignment. A milestone that still names a release that no longer exists is reported as a dangling reference by `papyrus check` (REQ-001.008).

Listing and viewing releases belong to REQ-002.002.

## Acceptance Criteria

- `papyrus release create <TITLE>` creates a release with a title and accepts an optional description, labels, and references.
- A release identifier uses the configured prefix and `id_padding`; with default configuration the first identifier is `REL-001`.
- A release may contain multiple milestones, and each milestone is assigned to at most one release.
- A new release starts `planned`, and its state is stored in the front-matter `status` field.
- The lifecycle is `planned -> released`, is not configurable, has no restore command, and treats archived as a file position.
- `papyrus release close <ID>` changes `planned` to `released`, and `released` means delivery happened.
- Closing a release that is not planned is rejected with a validation outcome and writes nothing.
- `papyrus release archive <ID>` moves the file to `<backlog_dir>/<release_dir>/archive`; the status is not modified.
- An archived release is hidden from active lists and from the Backlog board, keeps its identifier, remains viewable, and is not editable.
- `papyrus release edit <ID>` changes the title or description, and no option sets the lifecycle state apart from `close` and `archive`.
- `papyrus release delete <ID>` permanently removes the release, asks for confirmation, and `--force` skips the prompt.
- Archiving or deleting a release changes no milestone's file, state, or release assignment.
- A milestone that names a release that no longer exists is reported as a dangling reference by `papyrus check`.
